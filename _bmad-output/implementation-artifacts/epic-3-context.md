# Epic 3 Context: 장애 중에도 기록을 보호하고 도움받는 서비스 만들기

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Epic 1~2가 만든 계정·계획 기록을 장애 중에도 보호한다. 운영자는 일반 사용자 화면과 분리된 보호 표면에서 문제의 영향 범위만 정지하고, 강한 신호는 60초 안에 자동 정지되며, 복구는 검증 증거를 확인한 뒤 수동으로만 한다. 사용자는 장애·제한·복구 상태와 지금 쓸 수 있는 기능을 서비스 안 공지로 이해하고 문의할 수 있다. 안전한 배포·rollback, 이중 저장소 암호화 백업과 격리 복원, 개인정보 없는 관측·경보로 기록 손상과 노출을 막는다. 운영·출시 증거(정지 훈련, 실제 복원, 운영 배포 smoke)는 개발 자동시험과 구분해 기록하며 자동시험이 그것을 대체하지 않는다.

## Stories

- Story 3.1: 보호된 운영자 표면과 추가 전용 감사 원장
- Story 3.2: 영향 범위만 수동 제한
- Story 3.3: 강한 신호 감지와 60초 자동 정지
- Story 3.4: 검증 증거 확인 뒤 수동 복구
- Story 3.5: 제한·장애·복구 상태의 서비스 내부 공지
- Story 3.6: 사용자 문의 접수와 영업일 3일 답변 목표
- Story 3.7: 개인정보 없는 관측·경보와 운영 목표 계측
- Story 3.8: ARM64 단일 서버 blue/green 배포와 rollback
- Story 3.9: 일일 암호화 백업의 이중 보관과 30일 파기
- Story 3.10: 외부 복구 매니페스트 격리 복원과 삭제 계정 재활성화 차단

## Requirements & Constraints

- 운영자 권한은 배포 환경의 `(issuer, subject)` allowlist로만 부여·회수하고 사용자 UI에서 승격할 수 없다. 운영자 route·API·DOM은 일반 사용자 탐색·번들 초기 화면과 분리하며, 비운영자에게 권한 유무나 대상 존재 정보를 노출하지 않는다. 단일 운영자 MVP이므로 허위 이중 승인을 만들지 않되 모든 운영 command에 5분 재인증·일회성 행동 허가·필수 사유·증거·감사를 요구한다.
- 운영 command는 표준 envelope(불투명 operation ID, actor, command type, scope·target, 사유, 확인 hash, 정책 버전, 요청·결정 시각, idempotency key)로 수락한다. 빈 사유, 미지원 scope, 클라이언트가 권위를 주장하는 actor, 다른 입력의 같은 key는 거절한다. 최종 권한과 허가는 커밋 트랜잭션 안에서 재검사하고, 감사 기록 없는 상태 변경을 허용하지 않으며, 상태가 불명확하면 operation ID로 조회하게 하고 자동 성공 처리·재실행을 하지 않는다.
- 감사 원장은 PostgreSQL의 추가 전용 권위 원본이다. 요청·승인·거절·실패·완료를 actor·scope·reason·시각·결과·correlation으로 기록하고 이전 행을 수정·삭제하는 API를 두지 않는다. 원격 로그 유실과 무관하게 재현 가능해야 하며 API 비밀·세션·금융 상세·이메일을 담지 않는다. 일반 운영 명령 권한과 감사 조회·내보내기 권한은 분리하고 대량 추출은 별도 감사 사건이다.
- 제한 scope는 계획, portfolio, 계산 정책 버전, 연결, 동기화, 광고, 전역 기능이며 구체 scope가 전역보다 우선한다. 개별 입력 문제는 그 계획만, 공통 계산 문제는 그 계산 버전의 표시만, 공통 원인이나 범위 불명은 신규 연결·동기화 전역 정지다. 쓰기 권한 키 입력은 전역 정지가 아니라 그 연결 시도만 거부한다. 신규 연결·동기화·계산 표시·광고는 서로 독립적으로 정지할 수 있어야 한다.
- 강한 신호(쓰기 가능 키의 저장 단계 도달, 교차 사용자 접근 성공·공식 포인터 혼합, 비밀의 telemetry 검출, 같은 입력의 다른 결과 hash, portfolio·포인터 불변식 위반, source ID 의미 충돌, 미인식 Transaction Log enum, 다중 계정 schema·복호화 실패)는 감지 후 60초 안에 durable 제한을 만들고 자동 해제하지 않는다. 단일 사용자의 인증 만료·일반 timeout·rate limit·5xx·단일 가격 결측·광고 오류는 강한 신호가 아니다. 판정표·threshold·정책은 버전으로 고정한다.
- 운영 대응시간은 대한민국 영업일 09:00~18:00 KST다. 24시간 수동 대응을 약속하지 않으며 시간 밖에는 자동 정지가 일차 통제다. 수동 전역 정지는 경보 전달부터 5분 안이다. 복구는 원인 제거, 영향 범위 재현 시험, 고정 회귀·소유권·포인터 검사 통과, 새 배포·버전 증거가 있을 때만 수동 수행한다.
- 서비스 공지는 시작 시각, 영향 범위, 사용 가능한 기능, 다음 갱신 또는 복구 시각, 지원 경로를 담고 금융 상세값을 담지 않는다. 복구 뒤 종료 상태·시각을 같은 채널에 남기며 incident 버전·범위 변경·복구 이력은 불변이다. 효과 중인 제한에 대응하는 공지가 없으면 fail-closed다.
- 문의는 인증 사용자 웹 폼이 기본이고 공개 지원 이메일이 fallback이다. 실제 주소는 production 필수 설정이며 누락이면 readiness가 실패한다. 영업일은 `Asia/Seoul` 월~금에서 법정 공휴일을 뺀 날이고 공휴일은 연도별 versioned seed로 저장하며 다음 연도 자료가 없으면 그 연도 deadline 확정을 차단한다. 목표는 접수 다음 영업일부터 세 번째 영업일 18:00 KST이고 SLA로 표현하지 않는다. 일반 문의는 해결 후 90일 뒤 삭제한다. 문의 입력·로그에 금융 상세·자격정보를 금지한다.
- 관측은 운영 서버의 Grafana Alloy만 두고 Grafana Cloud와 외부 synthetic으로 본다. telemetry는 allowlist·redaction으로 사용자·금융·자격정보를 제거하고 낮은 cardinality label만 쓴다. 자격정보·세션 비밀·제공자 토큰·금융 상세값은 화면·URL·브라우저 저장소·로그·오류 추적·분석·광고 도구 어디에도 기록하지 않는다.
- 배포는 동일 ARM64 digest로 Worker drain → expand migration → inactive API readiness·smoke·telemetry → Nginx cutover 순이며 단일 migration 역할만 schema를 바꾸고 startup migration은 금지다. rollback 호환 창(old API+new schema, new API+new schema)을 유지하고 contract migration은 동시에 실행하지 않는다. 고가용성·무중단은 약속하지 않는다.
- 백업은 일일 custom dump를 앱 key와 별도 key로 암호화해 OCI와 OCI 밖 저장소 둘에 올리고, 단계별 종료코드·암호문 SHA-256·복호화 stream의 catalog 검사·두 업로드가 모두 성공한 generation만 성공으로 기록한다. 30일 회전 파기와 세대·용량 제한을 둔다. 복원은 OCI 밖 versioned recovery manifest로 격리 환경에서 하고, 복원 전 외부 deletion tombstone을 적용해 삭제 계정이 되살아나지 않게 한다. tombstone은 사용자 ID의 복구 불가 keyed digest·삭제 요청 ID·시각·영향 generation·파기 deadline만 담고 35일 뒤 파기한다.
- 사용자와 연결되는 문의·감사·운영 데이터는 도입 시점에 사용자 귀속·법정 보존 후보·순수 운영 데이터로 분류하고 허용된 삭제 경로를 시험한다. 법정 분리 보존의 필드·근거·목적·기간은 외부 법률·개인정보 승인(G-5) 전에 임의로 정하거나 production에 영구보존하지 않는다. 개발·CI 기본값은 법정 보존 `없음`이다. 삭제 상태를 이유로 필요한 파기 절차 자체를 중단하지 않는다.
- 핵심 운영 조작도 키보드·스크린리더로 쓸 수 있고 색상만으로 상태를 구분하지 않는다. 확인 대화상자는 대상·비가역 결과·삭제/보존 데이터를 먼저 설명하고 취소에 기본 포커스를 두며, 전역 운영 정지는 대상명 재입력을 요구한다. 320 CSS px·400% 확대에서 핵심 과업이 가능해야 하고 화면당 하나의 polite `role=status`만 동적 공지를 소유한다.

## Technical Decisions

- `operations` 모듈이 durable restriction, service notice, 보호된 운영자 command, 감사 원장을 소유한다. Epic 2가 연결·작업 접수·lease·발행·표시 경계에 이미 둔 제한 판독 지점은 이 모듈의 effective restriction을 fail-closed로 읽는다. 다른 모듈의 내부 entity·repository·table에 직접 접근하지 않으며 모듈 경계는 Spring Modulith 시험이 강제한다.
- 운영 command는 Epic 1의 재인증·세션 회전 계약과 서버 보관형 일회성 행동 허가(user·session·command·target·canonical confirmation hash 귀속, 5분 수명, 조건부 UPDATE 한 문장으로 소비, 성공 시 세션 재회전)를 그대로 재사용한다. 두 번째 인증 경로나 두 번째 허가 저장소를 만들지 않는다. 감사·제한·공지는 추가 전용 사실이고 현재 상태는 검증된 버전·포인터로 표현한다.
- 운영 제한 판정 시각의 권위는 PostgreSQL이며 애플리케이션 시계로 만료·효력을 판정하지 않는다. 강한 신호 판정표, 복구 조건, 공휴일 seed, telemetry allowlist는 모두 버전으로 저장하고 고정 fixture로 회귀 시험한다. 시간 의존 동작(60초 정지, 영업일 deadline, 백업 age, alert 지속시간)은 가상 시계 시험으로 고정한다.
- 운영 증거는 세 종류로 구분해 기록한다. 개발·CI 자동시험, 베타 전·월 1회 실제 훈련(60초 정지, 격리 복원, 운영 배포 smoke), 외부 승인 게이트(G-5 법률·개인정보, 실계정·IP). 자동시험이나 manifest 검사를 훈련 성공으로 표시하지 않고, 실패한 훈련을 완료로 기록하지 않는다. 운영 서버에는 개발용 관측 스택·Testcontainers·stub을 두지 않는다.
- 운영자 표면은 일반 사용자와 같은 동일 출처·CSP·세션 쿠키·오류 응답 계약 안에 있다. 새 경로는 Nginx 허용 목록과 프런트엔드 경로 맵을 함께 바꾸고 와일드카드 폴백은 두지 않는다. 운영자 제어를 일반 번들의 초기 화면에 섞지 않는다.

## UX & Interaction Patterns

- 운영자 제어는 보호 표면에서 연결·동기화·계산 표시·광고를 독립 제어하고 영향 미리보기(영향 기능·대상 수·남는 기능), 필수 사유, 확인, 검증 증거, 감사 기록을 한 흐름으로 제공한다. 전역 대상은 대상명 재입력이 필요하고 취소가 기본 포커스다.
- 사용자는 인증 뒤 서비스 공지에서 장애·제한의 영향 범위, 지금 가능한 기능, 다음 안내를 본다. 마지막 정상 기록은 공지와 분리해 유지하고 무의미한 재시도 버튼이나 허위 링크를 두지 않는다. 문의 채널·접수 상태·답변 기한은 설정 화면과 오류·제한 화면에서 보인다.
- 문의 폼은 오프라인·응답 유실·재시도에서 입력을 보존하고 자동 재시도하지 않으며 금융 원문·자격정보 첨부를 막는다. 로그아웃·세션 만료·삭제 뒤 뒤로 가기로 운영자·문의 화면이 복원되지 않아야 한다.

## Cross-Story Dependencies

- 순서는 **3.1 보호 표면·감사 원장 → 3.2 수동 제한 → 3.3 자동 정지 → 3.4 수동 복구 → 3.5 공지**다. 3.1이 권한 모델·행동 허가·command envelope·감사를 만들고 이후 모든 운영 command가 그것을 지난다. 3.2는 Epic 2가 둔 제한 판독 지점을 실제로 차단하는 첫 생산자이고, 3.3은 3.2의 제한을 신호가 자동으로 만들며, 3.4는 그 제한을 증거와 함께 푼다. 3.5는 효과 중인 제한을 사용자 공지로 매핑한다.
- 3.6 문의는 Epic 1 인증과 3.1·3.5 위에 서고, 3.7 관측은 3.1~3.6의 신호·지표를 모으며 3.3의 경보와 3.9의 backup age를 알린다. 3.8 배포는 3.2의 제한과 3.7의 telemetry를 전제하고, 3.9 백업 → 3.10 복원은 3.7 이후이며 Epic 1~2의 삭제 port와 tombstone 계약을 쓴다.
- Epic 1의 재인증·행동 허가·세션 회전과 identity 삭제 상태 계약, Epic 2의 제한 판독 기반·발행 포인터·공식 결과 표시를 소비한다. Epic 4(광고)는 없어도 광고 scope의 제한 상태를 관리할 수 있어야 한다. 계정 삭제의 외부 tombstone 저장·복원 전 적용 계약과 검증용 삭제 표본은 이 Epic이 만들고 실제 삭제 요청과의 최종 통합은 Epic 5가 한다.
- Epic 2 회고가 Epic 3 전에 처리하라고 남긴 것: 민감 command 공통 부품(세션 무장 Flow·멱등 키·lease 저장소·허가 무효화 단위) 통합, scope 제한·표시 단계 제한·해제의 제한 우회 근거를 3.2 SPEC 입력으로 넘기는 것, 그리고 운영자 표시 제한이 지나기 전 대시보드 훅·발행 서비스의 책임 분리다.
