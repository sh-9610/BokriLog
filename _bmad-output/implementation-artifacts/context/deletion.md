# 계정 소유권과 삭제

- **`identity`가 계정 소유권·삭제 상태의 유일한 권위다.** 다른 패키지는 공개 application API(`AccountLifecycleApi`·`AccountAccessApi`·`AccountDeletionApi`)로만 접근하고 `identity.internal`이나 소유 테이블에 직접 닿지 않는다. `identity`에는 HTTP 표면이 없다. 접근 거부는 `AccessDecision.DENIED` 하나이며 타 사용자·미존재·삭제된 대상이 구분되면 안 된다. 상태는 `ACTIVE → DELETION_IN_PROGRESS → DELETED` 단조 전진뿐이다. 어떤 모듈도 `org.springframework.security`에 의존하지 않는다 — 인증 표면의 사실(완료 확인 세션이 남기는 속성 이름)이 필요하면 모듈이 소유한 port를 루트가 구현한다(identity `CompletionSessionAttributes` → 루트 `CompletionSessionAttributesPort`, Epic 5 회고 A-2). `ModuleBoundaryTest`가 경계와 미노출을 강제한다.

**계정 삭제 (Epic 5)**
- 삭제 요청(5.1): 정책은 서버 상수 `AccountDeletionPolicy`(`ACCOUNT-DELETION-1.1` — 대상 code·백업 파기 30일·법정 분리 보존 빈 목록·고정 문구 `계정을 삭제합니다`·화면 고지 digest `NOTICE_DIGEST`) 하나이고 고지 hash는 그 정규 직렬화의 SHA-256이며, 화면의 닫힌 맵과 거절 code는 공유 표 `frontend/src/content/accountDeletionPolicy.fixture.json`을 두 층 시험이 함께 읽어 묶는다. 화면 고지 문장(삭제 대상·남기는 것·백업·법정 보존 없음)의 원본은 그 표의 `notice` 하나이고 화면이 그것을 읽는다. 표는 버전별 고지 digest 이력(`noticeDigestByVersion`)을 두고 백엔드 시험이 지금 버전의 행 = `NOTICE_DIGEST` = 표 `notice`에서 다시 계산한 값과 이력 digest가 서로 모두 다름을 단정한다 — 문장을 바꾸면 새 버전 행·버전·상수를 함께 올리고, 지금 행을 고쳐 쓰는 길은 기계가 막지 못해 리뷰가 이력 수정으로 본다(G-5 전 결정 D-3, `spec-g5-deletion-policy-defaults.md`). 요청은 민감 command `delete-account`(target `<userId>|<정책 버전>`, 확인 hash에 **입력한** 문구 — 등가가 아니면 `CONFIRMATION_MISMATCH`로 소비하지 않고 무장을 남긴다)이고, 확정은 허가 소비와 같은 트랜잭션에서 identity `AccountDeletionApi.requestDeletion`(생명주기 행 잠금 → 기존 행 판정 → `identity_deletion_request`(V30, 사용자당 하나) INSERT + `ACTIVE → DELETION_IN_PROGRESS`)을 부르며 부르는 운영 클래스는 `AccountDeletionRequestService` 하나다(`ModuleBoundaryTest`). 재전송 판정은 허가 경로보다 앞에서 요청 행의 멱등 키 digest로 한다(같은 키 200 같은 본문, 다른 키·삭제 중 준비 409 `ACCOUNT_DELETION_IN_PROGRESS`). 커밋 뒤 다른 세션 폐기(요청 세션 id만 남긴다) → 무장 폐기 → 재인증 시각 제거 순서이고 **세션 ID를 회전하지 않는다**(ERD §5 회전 규칙의 이 command 한정 예외 — `SessionRotation.completeSensitiveCommandWithoutRotation`, 응답 유실 뒤 같은 쿠키·같은 키 재전송이 같은 200을 받게 한다). 커밋 뒤 단계는 단계마다 따로 감싸 어떤 실패도 커밋된 요청을 오류 응답으로 바꾸지 않는다(단계 code 한 줄만 남는다). 준비·확정 본문은 화면이 본 정책 버전을 싣고 둘 다 서버 상수와 대조한다(409 `ACCOUNT_DELETION_POLICY_CHANGED`). 남은 요청 세션은 상태 조회·같은 요청 재전송·로그아웃만 쓴다(나머지는 기존 `DELETION_IN_PROGRESS` 거부 — 새 차단 장치 없음). 세션 응답은 요청이 있는 계정의 인증 세션과 재인증 표시 세션에만 `deletionInProgress: true`를 싣고 화면은 그때(재인증 표시보다 앞서) 어느 경로에서든 `DeletionProgressScreen`만 그린다(새 경로·복귀 목적지 없음). production(`BOKRILOG_ENV=production`)은 G-5 전이라 준비·확정 403 `ACCOUNT_DELETION_UNAVAILABLE`·조회 `available:false`다. 요청 행은 payload와 같은 운명이라 `erasePayload`가 지우고 `remainingRowsOf`가 세며, 복원 불변식은 요청 행 없는 `DELETION_IN_PROGRESS`와 요청 행이 있는데 `ACTIVE`인 계정을 위반으로 센다. 실제 모듈 삭제·tombstone·백업 파기는 5.2·5.3 몫이다(5.1).
- 삭제 실행(5.2): 요청 계정은 Worker·`all`의 `AccountErasureWorker`가 lease(30초, `sync.WorkerLease`)·heartbeat·fencing으로 집고 `AccountErasureRun`이 단계 `CREDENTIALS → PORTFOLIO → SYNC → PLAN → SOURCE → OPERATIONS → ENGAGEMENT → IDENTITY`를 단계마다 한 트랜잭션으로 돈다 — 단계 성공은 그 모듈 `remainingRowsOf` 0의 확인이고, `IDENTITY`는 앞 단계 전부의 잔여를 다시 세어 남은 단계를 `RESIDUAL_FOUND`로 되돌린 뒤에만 tombstone 기록·payload·세션·요청 행 삭제·`DELETED`·운영 완료 시각(`OPERATIONAL_DATA_ERASED` — 백업 파기 완료가 아니다)을 한 커밋으로 쓴다. 상태 권위는 identity 소유 V31 `identity_deletion_run`·`identity_deletion_step`(생명주기 행 FK, identity 잔여에서 제외)이다. 실패는 그 단계를 `RETRY_NEEDED`로 두고 멈추며 자동 재시도는 없다 — 다시 집는 것은 요청 세션의 `POST /api/account/deletion/retry`(재시도 필요일 때만 재대기열), 요청 세션을 잃은 실행의 운영 command `requeue-deletion`(Epic 5 회고 AI-1 — 원장 잠금 → 최종 권한 → 앞서 잠그지 않는 `SKIP LOCKED` 조건부 UPDATE 한 문장, 단계 상태 무변경, 키 digest는 운영자 전용 접두사, 원장 target은 요청 ID keyed digest, production 403 `DELETION_REQUEUE_UNAVAILABLE`, 호출자는 `OperatorCommandFacts` 하나, 실행의 재시도 키 digest를 운영자 것으로 덮으므로 그 전 사용자 재시도 키의 재전송은 409 `ACCOUNT_DELETION_NOT_RETRYABLE` — `spec-deletion-run-requeue.md`)와 기록조차 못 한 실행의 lease 만료 복구뿐이다. production(G-5 전)·tombstone 키 없는 프로세스는 집지 않는다. drain은 sync `DrainParticipant` SPI로 `WorkerDrain`의 같은 예산·종료 코드에 합류한다. Bybit 자격정보·소셜 연결 erase port는 ACTIVE 계정에서 아무것도 하지 않고, 문의 접수는 생명주기 잠금 아래 쓰기 접근을 다시 본다(operations port `AccountWriteAccess`). Worker당 동시 실행은 2(`MAX_IN_FLIGHT`)이고 단계 시작의 `hold`는 세대만 보고 같은 문장에서 lease를 민다(긴 단계도 이어진다). 단일 모드는 실행 행이 있으면 실행 행 → 생명주기 순서로 잠그고 그 실행을 마감한다(`finishRunBySingleErasure`). `IDENTITY`가 잔여를 찾으면 그 단계들만 재시도 필요가 되고 `IDENTITY`는 `PENDING`으로 남는다. 진행은 GET·재시도 응답만 지금 값을 싣고(`failedSteps`는 재시도 필요일 때만), 확정 응답은 고정값이라 5.1의 같은 키 재전송은 같은 본문이다. 재시도도 production에서는 403 `ACCOUNT_DELETION_UNAVAILABLE`이다. 진행 화면은 `progress{status,failedSteps}`(없거나 모르면 읽지 못함)로 재시도 필요·실패 범위·`삭제 다시 시도`를 그린다(`spec-5-2-account-data-erasure.md`).
- 백업 파기 추적(5.3): tombstone(`DELETION-TOMBSTONE-1.0`)은 Worker가 실행을 처음 집을 때 `CREDENTIALS` 앞 자기 트랜잭션에서 요청 시각(V30)으로 멱등 기록하고(실패는 첫 미완료 단계의 `TOMBSTONE_FAILED`, drain 중에도 기록), `IDENTITY`가 영향 generation 집합을 닫고 보존을 `max(요청, 운영 완료) + 35일`로 늘린다 — 줄이지 않는다. 상태 권위는 V32(tombstone `status PENDING|OVERDUE|DESTROYED`·`closed_at`·`destroyed_export`, 영향 generation 표 `operations_deletion_backup_generation`, 내보내기 기록 `operations_tombstone_export`, V31 실행의 `request_id`)이고 SQL은 `DeletionTombstoneRepository`·`BackupEventRepository`다. 영향 generation은 운영 완료 + 1시간(`BackupDestructionApi.CLOSURE_SLACK`, 커밋 전에 시작한 dump) 전에 `STARTED`한 저장된(`SUCCEEDED`) generation 전부(요청 전에 두 저장소에서 이미 파기된 것 제외, 하한 없음)이고, `DESTROYED`는 집합이 닫히고 여유가 지났고 모든 generation에 두 저장소 `AGE|COUNT|BYTES` `PURGED`(성공 기록이 있으면 순서 무관)가 있고 마지막 결과 없는 `STARTED`가 없을 때만이다 — 판정은 V24 기록만 보고 저장소를 조회하지 않는다(범위 밖은 deferred 174~176). 기한 `요청 + 30일`이 지난 미완료는 `OVERDUE`(감사 한 번, 백업을 앞당겨 지우지 않는다). 판정자는 루트 `BackupDestructionJudge`(Worker·`all`, 기본 5분, production에서도 돈다)가 열린 집합의 요청 ID → identity `operationalCompletions` → operations `BackupDestructionApi`로 잇고 tombstone마다 짧은 트랜잭션(`SKIP LOCKED`·lock 2초·statement 5초)이다. gauge 셋(`bokrilog.deletion.backup.destruction.due.soon`·`…overdue`·`bokrilog.tombstone.export.last.success.timestamp` seconds)과 경보 `DeletionBackupDestructionDueSoon`·`…Overdue`·`…Unmeasured`·`TombstoneExportStale`(1시간, critical)·`TombstoneExportUnmeasured`. 만료 삭제는 `DESTROYED`이고 그 상태로 성공한 사본(내보내기 번호 `destroyed_export`)에 실린 뒤 기한이 지난 행뿐이고 미완료 행은 기한과 무관하게 남고 내보낸다. 외부 사본 줄은 여덟 칸(`digest request_id requested_at destroy_after backup_deadline status OPEN|CLOSED gen_YYYYMMDD:<oci><offsite>,…`, 옛 네 칸도 읽는다)이고 `DESTROYED` 줄은 모든 generation `PP`만 받는다. 내보내기 성공은 업로드·대조·`latest` 갱신 뒤 기록 모드(`BOKRILOG_TOMBSTONE_EXPORT_CONFIRM`·`_EXPORT_ID`)가 쓰고, 기록 실패여도 24시간 지난 사본은 파기한다. 복원은 사본의 상태·파기 확인을 옮기고 같은 요청은 단조 병합하며, 닫힐 길 없는 열린 집합은 복원 적용 시각으로 닫는다(`closeRestored`, 호출자 `RestoreApplication` 하나). 감사는 `TombstoneAudit` 한 곳(`command=tombstone`, 수와 code만, 커밋 직전 `appendAtCommit` — 3.10 잠금 순서). tombstone 키는 API 슬롯 가운데 Worker만(그 밖에 `tombstone-export`·`restore-apply`·`deletion-sample`) — API 역할은 키가 있어도 bean이 없고 gate `TOMBSTONE_KEY_IN_API`가 거부한다. 5.3 이전 이미지의 worker·`tombstone-export`·`restore-apply`는 늘어난 보존·여덟 칸 줄을 읽지 못한다(`DEVELOPMENT.md`). 실저장소 파기는 미검증이다(`spec-5-3-backup-destruction-tracking.md`).
- 완료 검증·안내(5.4): 재가입 차단은 identity 소유 V33 `identity_deleted_identity`(사용자 열 없음, 단계 모드는 `request_id`)의 keyed digest다 — 입력 `deleted-identity:<issuer 길이>:<issuer>:<subject>`의 감사 digest 키 HMAC을 루트 port(`DeletedIdentityDigestPort` → operations `DeletedIdentityDigestApi`)가 계산하고 identity는 키를 갖지 않는다. 삭제 실행이 매핑을 지우는 트랜잭션(`CREDENTIALS` — 단계·단일·복원 재삭제)이 지우기 전에 기록하고 digest를 만들 수 없으면 지우지 않는다(fail-closed). 로그인은 기록이 있으면 계정을 만들지 않고(표지 `deleted`는 그 실행이 끝났거나 실행 행이 없을 때만, 미완료·판정 실패는 `failed`), 연결 INSERT는 술어와 성공 뒤 재확인으로 거부한다. 해제 command·문의 경로는 없고 기한이 해제다 — 판정 주기가 전체 삭제 완료 기록 뒤 `AccountDeletionRunApi.expireDeletedIdentities`로 그 요청의 실행이 `DELETION_COMPLETED`인 기록과 실행 행 없는 기록 가운데 기록 뒤 35일(DB 시각)이 지난 것을 지우고 실패는 WARN 한 줄로 접는다(D-4). 키 회전 시 기존 차단이 대조되지 않는다(139와 같은 주인). 요청 행은 요청 세션의 `spring_session.primary_id`를 남기고 `IDENTITY` 커밋이 그 세션을 지우지 않고 `principal_name`·CSRF/OAuth2 인가 요청 밖 속성을 걷어(남기는 두 이름은 루트가 identity port `CompletionSessionAttributes`로 준다 — identity는 Security 타입을 모른다) `identity_deletion_completion_session`(spring_session FK cascade — `spring_session`을 TRUNCATE하는 곳은 이 표를 함께 비운다)으로 요청 ID에 잇는다 — 이 완료 확인 세션은 미인증이고 닿는 경로는 완료 조회와 확정 재전송 거부(409 `ACCOUNT_DELETION_COMPLETED` — 5.1의 같은 키 재전송 200은 삭제가 끝나기 전까지다) 둘뿐이며, 세션 응답은 이 세션에만 `deletionCompleted: true`를 싣고(일반 미인증 본문 불변) 로그인 성공은 연결을 지운다(`DeletionCompletionSessions` 한 곳). 수명은 기존 유휴 30분·절대 12시간 그대로라 백업 파기(최대 30일)를 화면에서 다 보지 못할 수 있다(영수증 없음, 요청 ID와 지원 연락처로 안내). 전체 삭제 완료(`DELETION_COMPLETED`·`deletion_completed_at`)는 운영 완료 + tombstone `DESTROYED` + 법정 보존 처리(빈 목록이면 충족)일 때만 `BackupDestructionJudge`가 주기마다 기록하고(호출자 하나, 단조·멱등) 같은 주기가 되살아난 완료 세션 주체를 비운다(`scrubCompletionSessions`, 실패해도 서로 막지 않음). 복원 보고는 모듈별 잔여(`residual_<키>=`)를 싣고 합은 내역에서만 낸다. 운영자 원장 append는 원장 잠금 뒤 수행자가 삭제 중이면 귀속 없이 쓴다(162, 잠그지 않는 읽기). 실환경 격리 삭제·복원 통합시험(AC-5)은 `DEVELOPMENT.md`의 절차만 있고 **미수행**이다(`spec-5-4-deletion-completion-verification.md`).
