# 시험과 CI

- **판정 논리는 스크립트로.** CI 판정은 `.github/scripts/*.sh`가 소유하고 `test-ci-scripts.sh`가 계약을 단정한다. `ci.yml`의 인라인 `run`에 판정을 넣지 않는다. `ci.yml`을 바꾸면 그 시험도 함께 갱신한다.

## CI

`.github/workflows/ci.yml`이 유일한 workflow다. 구조는 `changes → frontend-quality·backend-quality·backend-assemble → (assemble) same-origin-integration·deploy-rehearsal·backup-rehearsal·restore-rehearsal → ci-required`이고(백업·복원 리허설은 backend jar만 기다려 배포 리허설과 병렬이다 — `spec-ci-critical-path.md`; backend jar의 생산자는 컴파일 + `bootJar`만 하는 `backend-assemble`이고 jar 소비 job 넷은 그것만 기다린다. `backend-quality`는 `build`로 시험을 돌되 jar를 올리지 않고, 두 job이 각자 낸 jar SHA-256 output을 `ci-required`의 집계가 대조한다 — bootJar는 `build.gradle.kts`의 재현 가능 archive 설정으로 바이트 단위 결정적이다. `spec-ci-backend-assemble-job.md`) 필수 검사 이름은 `ci-required`로 고정이다. GitHub ruleset `protect-integration-branches`가 `develop`·`main`에 PR 필수, merge commit만 허용, `ci-required` 필수(strict), 삭제·force push 금지를 건다.

- 첫 GitHub 실측(2026-09-06, PR #9): wall-clock 4분 3초. 문서-only 경로(`_bmad-output/**`, 최상위 `*.md`)는 `changes`와 `ci-required`만 돌아 1분 안에 끝난다.
- 백업·복원 리허설은 두 번째 분류 `backup-restore`를 따른다. PR의 변경이 전부 `frontend/**`·`_bmad-output/**`·최상위 `*.md`일 때만 `false`로 두 job을 승인된 비적용으로 건너뛰고, 그 밖(목록 밖 경로·비교 기준 없음·빈 diff·push·dispatch)은 `true`다. 게이트는 `!= 'false'`이고 집계는 빈 값(옛 분류기)을 `success` 기대로 읽는다(`spec-ci-critical-path.md`).
- artifact 이름에 `run_attempt`가 들어가 `Re-run failed jobs`는 쓸 수 없다. 재실행은 `Re-run all jobs`다. green이 아닌 시도는 재실행 전에 `ci-run-verdicts.md`에 한 행을 쓴다(PR은 그 행의 커밋이 재실행을 대신한다).
- 통합 job timeout 20분은 CI-PLAN §8의 시작값 5분과 다르다. `backend-quality`도 Story 1.3에서 10분 → 15분으로 올렸다(Testcontainers 콜드 실행). Story 2.11이 다시 `backend-quality`를 15 → 20분, 통합 job을 15 → 17분(회귀 단계 4 → 6분, 주입 origin Playwright `globalTimeout` 3 → 5분)으로 올렸다 — PR #49 실측이 백엔드 11분 5초·회귀 2분 30초였고 PR #52의 백엔드가 13분 0초였다. Story 2.17이 통합 job을 17 → 19분(회귀 단계 6 → 8분, `globalTimeout` 5 → 7분)으로 올렸다 — 로컬 CI 모드 회귀 실측이 4분 36초였다. Epic 5 회고 AI-4(`spec-ci-flaky-run-verdicts.md`)가 두 `Chromium headless shell 설치` 단계에 상한 3분을 두며(느린 apt 미러가 job 상한에 걸려 `cancelled`로 끝나던 것을 이름 있는 단계 실패로) 통합 job을 20분으로 올렸다. 로컬 백엔드 `clean build`는 시험 fork 분할 전 18분 36초(2026-10-15, Windows 11, 시험 1,496건)·19분 42초(2026-11-03, 분할 전 같은 날)였고, `maxParallelForks = 3`(`spec-ci-test-forks.md`) 뒤 같은 Windows 11에서 11분 44초(2026-11-03, 시험 1,610건·137 클래스, 클래스 시간 합 22.1분을 fork 셋이 11.1분 구간에 겹쳐 돌렸다)다. CI `backend-quality`는 분할 전 13~15분(PR #129 14분 19초)이었고 분할 뒤 PR #133에서 10분 14초(fork 2, 시험 1,625건)다(상세는 `DEVELOPMENT.md`). `deploy-rehearsal`은 백업 리허설을 떼며 70 → 30분, 새 `backup-rehearsal`은 50분이다. CI-PLAN 1.4.0(`architecture-BokriLog-2026-11-16/CI-PLAN.md`) §3이 2026-11-04~17 develop push의 job·단계 실측 표(제품 job n=18~19, `changes`·`ci-required`는 문서-only run 포함 n=34~36)를, §10이 보정 규칙과 job별 권장값을 적었다. `ci.yml`의 timeout은 아직 그대로이고 적용은 deferred 205(값은 209가 보정)다.
- Testcontainers는 러너의 docker 데몬을 그대로 쓴다. `backend-quality`에 서비스 컨테이너도, docker를 설치하는 action도 더하지 않았다. 시험은 기존 `Gradle 빌드` 단계 안에서 돈다.
- 로컬에서 CI 계약을 미리 확인하는 명령은 `bash .github/scripts/test-ci-scripts.sh`다.

**시험·CI**
- 순차 시험 중에도 scheduler·virtual worker는 실행된다. DB 초기화는 public 전체 테이블의 NOWAIT 잠금을 확보한 트랜잭션에서 하며, 경합이면 부분 잠금을 모두 롤백한 뒤 기다린다. 정리 시작 뒤 오류는 재시도하지 않는다(PR #63).
- 시험 클래스는 Gradle이 JVM(fork) 여럿에 class 단위 round-robin으로 나눈다(`maxParallelForks = 3`, 실제 수는 `min(3, --max-workers)` — CI는 2). JVM마다 PostgreSQL 컨테이너 하나(`PostgresTestcontainersConfig`의 static 컨테이너)이고, 컨테이너 수명은 JVM과 ryuk이 갖고 Spring 컨텍스트는 접속 정보(`JdbcConnectionDetails`)만 받는다 — 컨테이너를 bean으로 노출·주입하지 않는다(`spec-test-container-context-lifecycle.md`). 위 NOWAIT 잠금도 그 컨테이너 안이라 fork 사이에 DB·포트·파일을 공유하는 시험이 없어야 한다 — 서버 포트는 전부 임의(`RANDOM_PORT`·루프백 0)이고 고정 포트·`System.setProperty`·공유 파일 경로를 쓰는 시험을 들이지 않는다. JVM 안 병렬(JUnit `junit.jupiter.execution.parallel.*`)과 컨테이너 공유(`reuse`)는 쓰지 않는다(`spec-ci-test-forks.md`).
- 시험의 멱등 키·토큰 모양 값은 리터럴로 쓰지 않는다. gitleaks `generic-api-key`가 잡고, PR 커밋 범위가 스캔되므로 뒤 커밋으로는 지워지지 않는다(PR #60).
- `inert` 배경으로 돌려주는 대화상자의 초점 복귀만 passive 정리이고 나머지 초점 이동은 layout effect다(PR #57·#58, `DEVELOPMENT.md`).
- 광고 통합 시험은 `AdTestBase`(`OperatorTestBase` 상속, 새 시험 컨텍스트 없음)를 상속하고 그 helper(`grant`·`admitManual`·`backdateAdmission`·`claim`·`insertConsent`·`insertEligible`·`newTransition`·`assertNotFound`·`providerBackOn`)와 `OperatorTestBase.concurrently`의 사본을 만들지 않는다(`AdTestBaseTest`가 그 base의 하위 시험을 훑어 같은 이름의 재정의를 막는다 — 이름을 바꾼 사본과 인라인 SQL은 리뷰 몫이다). engagement의 바깥 의존이 `sync`·`operations`·`identity` 셋뿐인 것은 `ModuleBoundaryTest`가 강제한다(`spec-ad-test-commons.md`).
- 수집 중 lease 상실·수집 중 명령은 `PlanSyncTestBase`의 페이지 저장 문(`PageDoor` — 두 정수 advisory 키, 문마다 `PageDoorKey` objid)으로 만든다 — 만료형은 지정 페이지 저장 트랜잭션 안에서 계획 작업 lease를 만료시키고, 지연형은 페이지가 문 앞에 선 것을 본 뒤 명령을 `runBehindDoor`로 보낸다(`spec-lease-loss-test-doors.md`). 기계가 막는 것은 `src/test` 아래 시험 소스·resources의 `pg_sleep`(대소문자 무관)과 objid 중복뿐이다(`PageDoorSourceTest`).
