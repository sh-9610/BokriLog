# 백엔드 의존·스키마·실행

모듈의 공개 API 위치, 내부 구현 가시성, DB 접근 방식은 [모듈 레이아웃 규칙](finance.md)에 있다. 모듈 경계를 바꾸는 SPEC은 해당 파일도 `context`에 포함한다.

- **의존 추가는 SPEC이 승인한다.** JPA·`spring-security-test`는 아직 없다. 각각을 필요로 하는 스토리의 SPEC이 목적과 함께 승인할 때 추가한다. Actuator·`micrometer-registry-prometheus`는 `spec-3-7-observability-foundation.md`가 승인해 운영 classpath에 있고, Actuator에 닿는 설정은 루트 `TelemetryConfig` 한 곳이며 모듈은 Micrometer `MeterRegistry`만 쓴다(`ModuleBoundaryTest`가 모듈의 `boot.actuate` 의존을 막는다). PostgreSQL·Flyway는 `spec-1-3-identity-ownership.md`가, Spring Security OAuth2 Client·Spring Session JDBC는 `spec-1-4-google-sign-in.md`가 승인해 운영 classpath에, Spring Modulith·Testcontainers는 1.3 SPEC이 승인해 시험 classpath에 들어왔다. `ch.obermuhlner:big-math` 2.3.2는 `spec-2-7-first-plan-publication.md`가 승인해 운영 classpath에 있고, 쓰는 곳은 `calculation` 모듈 하나다(`ModuleBoundaryTest`가 강제한다). 경계 검증 라이브러리를 운영 jar에 싣지 않는다. 프런트엔드 런타임 의존 추가도 같다(개발·시험 전용 devDependency는 예외) — `web-vitals` 6.2.3(정확 버전)은 `spec-4-5-ad-telemetry-web-vitals.md`가 승인했고 쓰는 곳은 `frontend/src/telemetry/useTelemetry.ts` 하나다. 프런트엔드에는 라우터도 인증 SDK도 없다 — 경로 대응은 `App.tsx`의 닫힌 맵이고 로그인은 서버가 302로 처리한다.

- **스키마는 별도 migration 역할이 바꾼다(AD-12).** API 기동은 `Flyway::validate`만 하고 `migrate` 프로필만 실제로 마이그레이션한다(`SchemaValidationConfig`). 새 마이그레이션은 `backend/src/main/resources/db/migration/V<n>__<이름>.sql`로 더하고 이미 적용된 파일은 고치지 않는다.

`backend/`는 Java 25 + Spring Boot 4.1.1 + Gradle wrapper이고 모듈 경계는 Spring Modulith 2.1.1이 시험에서 검증한다(운영 classpath에는 없다). Story 1.3부터 PostgreSQL 18을 쓰고 Story 1.4부터 Spring Security OAuth2 Client·Spring Session JDBC가 있다. HTTP 엔드포인트는 `GET /api/status`, `GET /api/auth/session`, `POST /api/auth/logout`, `POST /api/auth/reauthenticate/<provider>`, 그리고 Spring Security 필터가 받는 `/api/auth/authorize/<provider>`·`/api/auth/callback/<provider>`다. Epic 2가 그 위에 `/api/connections/**`(Bybit 연결), `/api/snapshots/first/**`(첫 스냅샷·수집·판정·환산·계획 발행), `/api/plans/conditions/**`(계획 조건), `GET /api/dashboard`(공식 대시보드 — Story 2.8이 2.7의 `GET /api/plans/active`를 대체했고 옛 경로는 404다), `GET /api/dashboard/evidence`(현재 공식 결과의 계산 근거 — Story 2.9), `GET /api/dashboard/adjustments`(현재 공식 계산에 반영된 외부 자금흐름 조정 이력 — Story 2.10), `POST /api/dashboard/sync`(사용자 시점 증분 동기화 접수 — Story 2.11), `POST /api/dashboard/verification`(정밀 검증·기존 계획 계속 접수 — Story 2.12), `POST /api/dashboard/plan-end`와 그 `/confirm`·`/cancel`(활성 계획 중도 종료의 준비·확정·취소 — Story 2.13)를 더했다. Story 2.14는 새 경로 없이 `GET /api/dashboard`에 `COMPLETED` 상태를 더했다. Story 2.16이 `POST /api/connections/bybit/revocation`과 그 `/confirm`·`/cancel`(Bybit 연결 해제의 준비·확정·취소)을 더했다. Story 3.1이 보호된 운영자 표면 `/api/operator/**`(`GET /api/operator/audit` 감사 조회, `GET /api/operator/operations/{id}` operation 조회, `POST /api/operator/commands/audit-export`와 그 `/confirm`·`/cancel`)를 더했다 — 인증된 비운영자·권한 부족은 어느 경로·메서드에서도 없는 경로와 같은 404다(`OperatorGate`). Story 3.2가 같은 세 경로에 제한 생성 command 넷(`restrict-new-connection`·`restrict-sync`·`restrict-calculation-display`·`restrict-advertising`)과 `GET /api/operator/restrictions`(활성 제한, command 권한)를 더했고, 계산 표시 제한 중에는 `GET /api/dashboard`가 `result` 없이 `calculationDisplay: "RESTRICTED"`를, 근거·조정 이력이 409 `CALCULATION_DISPLAY_RESTRICTED`를 낸다. Story 3.5가 인증 사용자의 `GET /api/notices`(그 사용자에게 적용되는 효력 제한과 그것을 덮는 최신 공지 — `ServiceNoticeController`)와 운영 command `publish-notice`·`GET /api/operator/notices`(사건·버전 이력, command 권한)를 더했다. Story 3.6이 사용자 문의 `GET`·`POST /api/support/inquiries`(내 문의·접수, CSRF·`Origin`·멱등 키)와 운영자 `GET /api/operator/inquiries`·`/{reference}`·`/metrics`(command 권한), 운영 command `update-inquiry`를 더했다. Story 4.1이 인증 사용자의 광고 동의 `GET`·`POST /api/engagement/ad-consent`(조회·선택·철회, `POST`는 CSRF·`Origin`·멱등 키 — `AdConsentController`)를 더했고, Story 4.2가 `POST /api/engagement/ad-eligibility`(수동 동기화 성공 결과의 광고 자격·빈도 제한 판정, CSRF·`Origin` — `AdEligibilityController`)를, Story 4.3이 `POST /api/engagement/ad-transition`(자격 `transition`의 1회 소비, CSRF·`Origin` — `AdTransitionController`)을, Story 4.5가 `POST /api/engagement/telemetry`(Web Vitals·광고 이벤트 beacon, CSRF·`Origin` — `ClientTelemetryController`)를 더했다. Story 5.1이 인증 사용자의 계정 삭제 요청 `GET /api/account/deletion`(삭제 정책·요청 상태 — 삭제 진행 세션도 읽는다)·`POST /api/account/deletion`과 그 `/confirm`·`/cancel`(준비·확정·취소, CSRF·`Origin`, 확정은 멱등 키 — `AccountDeletionController`)을 더했고, Story 5.2가 삭제 진행 세션의 `POST /api/account/deletion/retry`(재시도 필요인 삭제 실행의 재대기열, CSRF·`Origin`·멱등 키, 재인증 없음)를 더했다. Epic 5 회고 AI-1이 운영 command `requeue-deletion`(target 삭제 요청 ID `del_…`, 요청 세션을 잃은 재시도 필요 실행의 재대기열)과 `GET /api/operator/deletions`(재시도 필요 실행 목록, command 권한, production은 `available:false`)를 더했다. 상태·인증 컨트롤러는 루트 패키지 `com.bokrilog`에 있고 모듈 패키지는 `identity`·`source`·`portfolio`·`operations`·`sync`·`plan`·`calculation`·`engagement` 여덟이다(`calculation`은 DB·Spring·시계·다른 모듈에 의존하지 않는 순수 모듈이다). `ARCHITECTURE-SPINE.md`가 적은 여덟 번째 모듈 `engagement`(광고 동의·빈도 제한)는 Story 4.1이 만들었고 지금은 광고 동의와 광고 자격·빈도 제한(4.2)·transition 소비(4.3)·브라우저 계측과 광고 성능 kill switch 판정(4.5)을 소유한다. Story 1.9부터 루트 패키지가 자기 테이블 하나(`action_grant`, `V3`)를 소유한다 — 그전까지 모든 테이블은 `identity` 소유였다. 민감 command의 공통 부품은 셋이다 — 세션 무장 메커니즘 `SessionArming<T>`(루트, 일곱 Flow가 위임 — 계정 삭제 `AccountDeletionFlow` 포함), 실행 성공 뒤의 재인증 시각 제거·세션 회전 `SessionRotation`(루트), 멱등 키 규칙·헤더·code `com.bokrilog.sync.IdempotencyKey`(메시지 한 문장은 `ApiErrorHandler.MESSAGE_IDEMPOTENCY_KEY_REQUIRED`) — 새 민감 command는 이 셋을 쓰고 사본을 만들지 않는다. 루트 패키지 HTTP 표면(컨트롤러·`OperatorGate` 필터·`AuthFlowHandlers`)의 공통 판독·응답은 package-private `ControllerSupport` 한 곳이다 — 세션 사용자 `currentUserId`, 없는 경로와 같은 404로 답하는 SENSITIVE 판정 `allowedUser(AccountAccessApi)`, correlation id `correlationIdOf(HttpServletRequest)`, JSON·`no-store` 오류 응답 `error`와 전용 오류 record용 `noStoreJson`(403을 내는 사용자 판정·WRITE 접근·전용 record의 판정과 본문은 각 호출자가 그대로 가진다). 멱등 충돌 code는 `IdempotencyKey.CONFLICT_CODE` 하나다. 새 코드는 세션 사용자 판독·SENSITIVE 판정·요청 식별자 헤더 판독의 사본도 `"IDEMPOTENCY_CONFLICT"` 리터럴도 만들지 않는다 — `ControllerSupportTest`가 운영 소스(`backend/src/main/java`)를 훑어 `UUID currentUserId(`·`UUID allowedUser(` 정의와 한 문장 안의 `UUID.fromString(`…`getName()`이 `ControllerSupport`에만, `getHeader(ApiErrorHandler.REQUEST_ID_HEADER)`가 `ControllerSupport`에만(한정자 없는 꼴은 상수를 소유한 `ApiErrorHandler`에도), 그 리터럴이 `IdempotencyKey`에만 있음을 단정한다. 그와 별개로 작업 lease 30초의 SQL 조각은 `sync.internal.SyncLease` 한 곳이 소유하고 `SyncLeaseTest`가 운영 소스에 리터럴이 다시 생기지 않게 막는다. 컴파일 경고는 `-Werror`로 실패다.

제공자 자격정보는 여전히 필요 없다. 판정은 **제공자마다 독립**이다 — `BOKRILOG_PUBLIC_BASE_URL`과 그 제공자의 `BOKRILOG_<제공자>_CLIENT_ID`·`_CLIENT_SECRET` 중 하나라도 비면 그 등록만 만들어지지 않고 그 제공자의 인증 시작이 공통 오류 계약으로 fail-closed이며, 다른 제공자의 로그인은 살아 있다. 어느 제공자도 구성되지 않으면 `oauth2Login` DSL 자체를 배선하지 않는다. 서로 다른 두 등록이 같은 issuer로 해석되면 기동을 거부한다 — 조회 키가 `(issuer, subject)`라서 override 하나로 계정 병합이 열리기 때문이다(`DevOidcStubProfileTest`·`AuthNaverSignInTest`가 이 계약을 지킨다). 정상 흐름의 결정성은 `dev-oidc` 프로필에서만 사는 local OIDC 스텁이 만든다. 스텁 논리는 `DevOidcStub`이 소유하고 표면은 두 곳이다 — 개발·CI 스택은 `DevOidcStubConfig`가 `/api/dev-oidc/<제공자>/**`에 제공자마다 인스턴스 하나로 올리고(라우터 빈은 하나다)(브라우저와 백엔드가 같은 origin에서 도달해야 성공 경로를 브라우저 층에서 검증할 수 있다), 백엔드 시험은 `OidcStubConfiguration`이 루프백 HTTP 서버에 올린다. 스텁을 두 번 만들지 않는다. 그 프로필이 어느 제공자든 실제 등록과 함께 활성이면 기동을 거부하고, 실제 제공자 왕복은 Epic 1의 **실연동 미검증** 게이트가 소유한다. 백엔드가 자기 스텁에 닿는 주소는 `BOKRILOG_DEV_OIDC_INTERNAL_BASE_URL`이며 브라우저가 보는 origin과 다른 값이다.

리다이렉트의 `Location`은 origin-상대 경로다(`server.tomcat.use-relative-redirects: true`). 기본값에서는 Tomcat이 요청 `Host`로 절대 URI를 만들고 Nginx가 포트를 잃은 값을 넘기므로 로그인 뒤의 이동이 80번 포트로 끊긴다.

**백엔드 시험은 Docker를 전제한다.** Testcontainers가 실제 `postgres:18.6-alpine`을 JVM당 하나 띄운다(`build`는 시험 클래스를 JVM 여럿에 나눈다 — fork 수가 `min(3, --max-workers)`이고 `--max-workers` 기본이 CPU 수라 4코어 이상 기기는 fork 3·컨테이너 3, 2코어 기기와 CI(private 저장소 기본 러너, PR #133 실측 executor 2개)는 fork 2·컨테이너 2다). 데몬이 없으면 `build`가 컨테이너 시작 실패로 멈추며, 인메모리 데이터베이스로 대체하지 않는다.

JDK 25가 필요하고 toolchain 자동 프로비저닝은 꺼져 있다. macOS는 `brew install openjdk@25` 뒤 사용자 홈에 최초 1회 심볼릭 링크를 걸면 `/usr/libexec/java_home -v 25`와 Gradle이 함께 찾는다(sudo 불필요). Windows는 `winget install EclipseAdoptium.Temurin.25.JDK`로 끝난다. PATH의 `java -version`이 17로 남아 있어도 정상이다. `JAVA_HOME`을 셸에서 바꿔 두지 않는다.

```bash
mkdir -p ~/Library/Java/JavaVirtualMachines
ln -sfn /opt/homebrew/opt/openjdk@25/libexec/openjdk.jdk ~/Library/Java/JavaVirtualMachines/openjdk-25.jdk
backend/gradlew --project-dir backend build
```
