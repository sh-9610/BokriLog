## Goal

사용자가 최근 재인증과 명시적 확인(대상명 재입력)을 거쳐 계정 삭제를 요청하면 즉시 모든 세션·자격정보·민감 접근을 막고, 인증·금융·계획·지원·광고 데이터를 모듈별 deletion port로 실제 제거하며, 백업에 남은 사본도 외부 tombstone으로 복원을 막은 채 요청일부터 최대 30일 안에 파기한다. 운영 데이터 삭제·백업 파기·법정 분리 보존·실패를 서로 다른 상태로 사실대로 보여 주고, 부분 실패를 완료로 숨기지 않는다. 삭제 가능성을 이 Epic에서 처음 설계하는 것이 아니다 — 삭제 상태·접근 차단 계약(Epic 1)과 모듈별 삭제 경로·tombstone·격리 복원(Epic 1~4, Story 3.9~3.10)은 이미 있고, 이 Epic은 사용자 요청과 전체 삭제·백업 파기·복원 방지를 하나로 묶어 FR-19를 완성한다. 법정 분리 보존 정책(게이트 G-5)은 법률·개인정보 승인 전이므로 개발·CI는 "분리 보존 없음·전부 삭제" 기본값으로 구현하고, production 삭제 실행과 공개 베타는 승인 전까지 차단한다.

## Stories

- Story 5.1: 삭제 범위와 보존 정책을 확인하고 계정 삭제 요청하기
- Story 5.2: 모든 모듈의 사용자 데이터를 삭제하고 부분 실패 추적하기
- Story 5.3: 외부 tombstone으로 복원을 차단하고 30일 내 백업 파기 추적하기
- Story 5.4: 삭제 계정이 복원 후 재활성화되지 않음을 통합 검증하고 완료 안내하기

## Requirements & Constraints

- **삭제 대상.** 소셜 로그인 연결·제공자 토큰, 세션, Bybit 자격정보, provider account·connection·membership, 원 사건·source fact/snapshot, portfolio snapshot·component·pointer, 계획·계산 결과·버전·공식 pointer, 작업 데이터, 문의, 광고 동의·시도·빈도 제한, 사용자 귀속 운영 데이터 전부. 금융·계획 데이터를 분쟁 대비·분석 목적으로 임의 보존하지 않는다. 사용자 식별이 없는 공유 데이터(예: 공개 시장 가격 증거, 비식별 계측 표본)와 다른 사용자 데이터는 보존한다.
- **요청 개방.** 현재 수단으로 최근 재인증한 뒤 user·session·`DELETE_ACCOUNT`·정책 version·TTL·확인 hash에 귀속된 일회성 허가와 계정 표시명 재입력을 요구한다. CSRF·동일 출처·삭제 상태를 재검사하고 request·시작 시각·정책 version(및 사용자 고지 hash)을 원자 생성한다.
- **즉시 차단.** 요청 생성과 동시에 모든 세션·자격정보·민감 화면·일반 쓰기·중복 요청을 막는다. 실행 중에도 로그인·OIDC 콜백·Worker·광고 callback·문의 제출이 삭제 상태를 다시 보고 데이터·세션·공식 pointer를 재생성하지 못해야 한다. 작업 시작 시점의 허용 상태만 믿지 않는다.
- **멱등·부분 실패.** 응답 유실·반복 요청은 같은 operation을 돌려준다. 각 port는 target user에 멱등하고 결과·건수·오류를 금융 상세 없이 반환한다. 일부 실패는 `재시도 필요`로 남고 완료로 표시하지 않으며, 성공한 port 재실행은 안전하고 실패 범위만 명시적으로 재시도한다(자동 재시도 루프 없음).
- **완료 판정 분리.** 모든 운영 port와 승인된 법정 분리 이동이 검증돼야 `운영 데이터 삭제 완료`이고, 백업 파기 완료와는 별도 상태다. 모든 필수 증거(운영 삭제·백업 파기·법정 보존 처리)가 있어야만 전체 삭제 완료로 전환한다.
- **백업 30일.** 요청일부터 최대 30일 안에 해당 계정이 들어 있을 수 있는 모든 generation을 두 저장소와 임시본에서 파기하거나 승인된 crypto-erasure로 접근 불가화한다. object·key·검증 증거가 모두 있어야 완료이며, 한 저장소 실패·기한 임박/초과는 완료가 아니라 alert·감사·재시도를 만든다. 가상 시계 시험을 실제 object 파기 증거로 대체하지 않는다.
- **tombstone.** 서비스 DB·백업과 분리해 암호화하고 비식별 keyed digest·삭제 request ID·시각·영향 backup generation·파기 기한·상태·정책 버전만 담는다(`DELETION-TOMBSTONE-1.0`, 35일 보존 — 백업 최대 수명 30일보다 길게). 금융 상세·credential·소셜 원 식별자는 금지다. 모든 restore는 공개 전에 tombstone을 적용하고, 접근·사용·파기를 최소 권한으로 감사하며, 승인 기간 전 소실로 삭제 계정이 되살아날 위험을 막는다.
- **복원 후 재활성화 금지.** 같은 OIDC identity 로그인, 오래된 cookie, 대기 중 Worker·callback·멱등 재전송이 삭제 계정을 복구하거나 빈 신규 계정을 자동 생성하지 못한다. 삭제 완료 뒤 신규 가입 허용 여부는 G-5 정책만 따른다.
- **누출 금지.** 허가·금융 상세·보존 원값을 로그·분석·오류 응답에 남기지 않는다.
- **외부 게이트.** G-5(법정 분리 보존 대상·근거·목적·기간·고지의 법률·개인정보 승인) 전에는 production 삭제 실행과 공개 베타를 차단하고, 화면·정책 일치와 미승인 실행 차단을 시험한다. 베타 전 실제 격리 환경의 삭제·복원 통합시험(NFR-18)은 자동시험과 별도 상태로 기록하며 자동시험만으로 출시 게이트를 통과시키지 않는다.

## Technical Decisions

- `identity`가 삭제 상태와 orchestration의 유일한 권위다. 상태는 `ACTIVE → DELETION_IN_PROGRESS → DELETED` 단조 전진이고, 다른 모듈은 공개 application API로만 닿으며 별도 삭제 상태를 권위 원본으로 만들지 않는다. `identity`에는 HTTP 표면이 없으므로 사용자 요청 표면은 루트 패키지가 맡는다.
- 각 모듈 공개 deletion port는 자기 소유 데이터만 처리한다. 순서는 session·OIDC token·Bybit credential 폐기가 먼저다. 순수 `calculation` 모듈에는 저장소·삭제 기능을 만들지 않는다.
- 추가 전용 사실(원 사건·자금흐름·스냅샷·계산 버전·감사)의 삭제는 검증된 계정 삭제 경로에서만 허용되는 명시적 예외다. Bybit 연결 해제나 일반 데이터 변경을 계정 삭제로 취급하지 않는다.
- 민감 command 계약을 그대로 쓴다 — 5분 안 일회성 action grant(user·session·command·target·확인 hash 귀속, 1회 소비), 성공 시 세션 회전, 멱등 키. 기존 공통 부품(세션 무장·세션 회전·멱등 키, 프런트엔드 확인 대화상자·동일 출처 POST helper)의 사본을 만들지 않는다.
- 개발·CI 기본값은 "법정 분리 보존 없음·모든 사용자 데이터 삭제"이며, 이것을 production 법률 판단으로 기록하지 않는다. 법률 검토가 tombstone에 필드를 더 요구하면 production 활성화 전 별도 승인 변경으로 반영한다.
- 백업은 기존 일일 암호화 dump의 이중 보관(OCI·OCI 밖)과 30일 회전 파기, 복원은 versioned recovery manifest의 격리 복원 절차 위에 선다. 파기·tombstone·삭제 단계의 기록은 기존 운영 원장·감사 규칙과 관측 allowlist/redaction을 따른다.

## UX & Interaction Patterns

- 진입은 연결·개인정보 설정의 `계정 삭제` 전용 흐름이다. 화면은 즉시 접근 차단, 운영 데이터 삭제 대상(자격정보·계획·외부 자금흐름·스냅샷·계산 버전 등 열거), 백업 최대 30일 파기 예정일, 승인된 법정 분리 보존의 필드·근거·목적·기간을 서로 구분해 보여 주고, 연결 해제(기록 보존)와 무엇이 다른지 설명한다.
- `confirmation-dialog`: 대상·비가역 결과·삭제/보존 데이터를 먼저 말하고 기본 포커스는 취소, 계정 삭제는 대상명 재입력을 요구한다. 키보드·확대·낭독을 지원한다.
- 진행 중에는 중복 제출과 민감 표면 접근을 막고 진행·실패 범위·명시적 재시도 상태만 보여 준다. 부분 실패·기한 초과를 숨기지 않으며 자동 재시도하지 않고 지원 경로를 함께 제공한다. 정책 미확정이면 실행을 열지 않는다.
- 완료되면 세션이 끝나고 완료 확인만 표시한다. 운영 삭제 시각, 백업 파기 예정일/완료, 승인된 법정 보존 대상·목적·기간을 사실대로 표시한다. 이전 URL·뒤로 가기(bfcache)·다른 계정 로그인으로 삭제된 금융 화면을 다시 열 수 없어야 한다.
- `복리 계획 비교`·비추천 고지 인접 배치와 화면당 live region 하나 규칙은 그대로다.

## Cross-Story Dependencies

- 순서는 **5.1 요청·즉시 차단 → 5.2 모듈 삭제·부분 실패 → 5.3 tombstone·백업 파기 추적 → 5.4 복원 통합 검증·완료 안내**다. 5.1은 실제 모듈 삭제·백업 파기를 하지 않고, 5.2는 backup object 파기를 하지 않는다. 5.3은 3.9~3.10과 5.1~5.2를, 5.4는 5.1~5.3과 3.10을 전제한다.
- Epic 1: 삭제 상태·접근 차단 공개 API(1.3), 재인증·action grant·세션 회전(1.8·1.9), 세션 폐기 규칙(1.5)을 그대로 쓴다.
- Epic 2~4: 각 모듈 deletion port와 삭제 상태 소비(늦은 Worker 발행 차단 포함)는 데이터 도입 스토리가 이미 구현·시험했다. 이 Epic은 그것을 연결하며, 새 저장 위치를 만들면 삭제 계약을 같은 작업에서 넓힌다.
- Epic 3: 지금의 계정 삭제는 루트 `AccountErasure` 한 트랜잭션이고 사용자 경로가 없다(호출자는 리허설용 삭제 표본과 복원 적용뿐이며 `ModuleBoundaryTest`가 고정). 5.1·5.2가 사용자 경로를 열 때 이 고정과, 5.2가 요구하는 port별 상태·부분 실패·실패 범위 재시도와 단일 트랜잭션 구조의 관계를 함께 정해야 한다. tombstone outbox(V25)는 지금 digest·요청 ID·시각·+35일 기한만 담고 외부 내보내기·격리 복원의 tombstone 선적용·계정 재삭제는 3.10이 리허설까지 만들었다 — 5.3은 generation 영향·파기 상태·정책 버전 추적과 실제 파기 증거를, 5.4는 실제 격리 복원 증거를 더한다. 운영자 거절·실패 행이 삭제 커밋 뒤 append될 때의 `actor_user_id`(`deferred-work.md` 162)는 5.2·5.4를 결정 지점으로 지목한다.
- 외부: G-5 법률·개인정보 승인과 실제 저장소·격리 환경 검증(3.9·3.10의 미검증 증거)은 출시 게이트가 소유하며 이 Epic의 개발 완료와 구분한다.

## Story 5.1이 확정한 예외

위 요구·기술 결정 가운데 다음 셋은 Story 5.1(`spec-5-1-account-deletion-request.md`)이 사용자 결정(2026-11-05)으로 바꿨다. 5.2~5.4는 이 절을 우선한다.

- **확인 대상은 고정 문구다.** 계정 표시명·이메일을 저장하지 않으므로 확인은 고정 문구 `계정을 삭제합니다` 재입력이다(accepted deviation). command 이름은 `delete-account`다.
- **삭제 확정은 세션 ID를 회전하지 않는다.** 확정 뒤 다른 세션 폐기 → 무장 폐기 → 재인증 시각 제거만 하고 요청 세션 ID는 그대로다 — 회전된 쿠키가 실린 응답이 유실되면 같은 키 재전송이 401이 되고 삭제 중 계정은 재로그인도 거부되기 때문이다(민감 command 회전 규칙의 이 command 한정 예외). 커밋 뒤 단계의 실패는 커밋된 요청을 오류로 바꾸지 않는다.
- **요청 세션 하나만 상태 전용으로 남는다.** 즉시 차단(AC-3 "모든 세션")의 예외다 — 그 세션은 삭제 상태 조회·같은 요청 재전송·로그아웃만 한다.
