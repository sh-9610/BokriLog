## Goal

사용자가 Google·네이버·카카오 중 하나로 가입·로그인하고, 최근 재인증을 거쳐 다른 로그인 수단을 연결·해제하며 동일한 내부 계정을 안전하게 사용할 수 있게 한다. 이 에픽은 사용자 데이터 경계(내부 `user_id` 소유권 검증), 서버 세션 보안, 이메일 자동 병합 금지, 마지막 로그인 수단 보호를 확립하고, 이후 모든 모듈이 사용할 삭제 상태 계약을 `identity` 모듈에 마련한다. Story 1.1이 프런트엔드의 최초 실행 기반과 디자인 토큰·테스트 기반을 이미 만들었고, Story 1.2~1.3이 백엔드·데이터베이스의 최초 실행 기반과 남은 프로젝트 구조를 만든다. 계획이나 Bybit 연결 없이도 가입·로그인·로그아웃·로그인 수단 관리가 실제 서버와 저장소를 통해 작동하면 이 에픽은 독립적으로 완료된다.

## Requirements & Constraints

- 인증 세션이 유일한 내부 `user_id`를 결정한다. 모든 사용자 소유 조회·변경은 서버가 이 ID로 소유권을 검증하고, 클라이언트가 보낸 소유자 ID는 권위가 아니다. 교차 사용자 접근은 0건이어야 하며, 타 사용자 대상과 미존재 대상은 동일한 외부 오류 코드·응답 계약을 사용해 존재 여부를 노출하지 않는다.
- `(issuer, subject)`는 전역 유일하고 `(user_id, provider)`도 유일하다. 이메일·표시명은 식별키가 아니며 이메일 일치로 계정을 자동 생성·병합·전환하지 않는다. 이미 다른 사용자에 연결된 식별자는 어느 계정인지 밝히지 않고 거부한다.
- 마지막 남은 로그인 수단은 해제할 수 없다. 로그인 수단 연결·해제, 계정 삭제 등 민감 작업은 최근 재인증과 명시적 확인을 요구한다. 제공자 실패 시 어떤 상태도 변경되지 않아야 한다.
- 제공자 토큰, authorization code, PKCE verifier, `subject`, 세션 비밀, 재인증 허가는 화면·URL·브라우저 저장소·구조화 로그·오류 문맥·추적·지표 label·분석 이벤트·광고 payload·HTTP 오류 응답 어디에도 남기지 않는다.
- 기본 동의 범위는 `openid`와 제공자별 최소 식별 정보뿐이다. 이메일·프로필은 제품 기능에 필요해질 때 목적 설명과 함께 별도 최소 동의로 요청하며 마케팅·연락처·게시 권한은 로그인과 묶지 않는다.
- `identity`가 도입한 사용자·소셜 식별자·세션·보유 제공자 토큰의 삭제 경로를 모듈 수준에서 시험한다. 부분 실패를 삭제 완료로 보고하지 않는다. 실제 사용자 삭제 요청 개방과 전체 삭제 조율은 이 에픽 범위 밖이다.
- 핵심 화면 성능 목표는 p75 기준 LCP 2.5초 이하, INP 200ms 이하, CLS 0.1 이하다. 핵심 값·상태·조작은 키보드로 접근 가능하고 색상만으로 구분하지 않는다.
- 개발·CI 스텁과 계약 시험 통과는 개별 스토리의 완료 증거다. 에픽의 **실연동 검증 완료**는 세 제공자의 실제 가입·로그인·재인증과 지원되는 모든 연결 방향을 등록된 클라이언트로 통과한 뒤에만 선언하며, 그 전까지는 **실연동 미검증** 상태를 유지한다. 에픽 기능 완성이 공개 베타 승인을 뜻하지는 않는다.

## Technical Decisions

- **스택 기준선:** 백엔드 Java 25 LTS + Spring Boot 4.1.x, Spring Modulith 2.1.x, Spring Session JDBC, PostgreSQL 18.x. 프런트엔드 React 19.2.x + Vite 8.2.x 정적 SPA. 진입점 Nginx 1.30.x stable. 운영 이미지는 `linux/arm64`로 CI 검증하고 tag가 아닌 digest로 배포한다.
- **구조:** 포트/어댑터를 쓰는 모듈형 모놀리스. 백엔드 패키지는 `identity`, `source`, `portfolio`, `sync`, `plan`, `calculation`, `engagement`, `operations`로 나누고 그 밖에 `frontend/`와 `deploy/`(compose·nginx·alloy·terraform)를 둔다. Epic 1은 `identity`와 프런트엔드·Nginx·compose 기반만 도입한다. 모듈은 다른 모듈의 공개 application API에만 의존하며, 내부 entity·repository·소유 테이블 직접 접근과 순환 의존은 Spring Modulith 경계 검증으로 CI에서 차단한다. API와 Worker는 같은 이미지의 별도 프로세스이며 Epic 1에는 Worker가 필요 없다.
- **동일 출처 셸:** Nginx가 정적 SPA를 제공하고 같은 오리진의 `/api`만 프록시한다. 임의 경로를 API나 외부 주소로 프록시하지 않는다. 공식 계산·권한·신뢰 상태는 서버만 변경하며 브라우저 영속 저장소에 인증 토큰이나 금융 원본을 두지 않는다. 오류 응답은 성공·빈 데이터로 위장하지 않고 안정적인 machine code·사용자 메시지·correlation ID만 반환하며 내부 경로·스택·환경 비밀을 노출하지 않는다.
- **세션 모델:** 브라우저에는 HttpOnly·Secure·SameSite=Lax 불투명 쿠키만 두고 세션은 Spring Session JDBC로 PostgreSQL에 저장한다(업무 데이터·세션·작업 큐 단일 저장소). 로그인·재인증 성공과 허가 소비 시 세션 ID를 회전한다. 인증·재인증·연결·해제의 모든 상태 변경 요청은 세션 귀속 CSRF 토큰과 동일 출처 `Origin` 검증을 통과해야 한다.
- **OIDC 공통 불변식:** Authorization Code + PKCE(S256), 서버가 발급해 인증 세션·제공자·흐름·정확한 redirect URI에 귀속한 짧은 만료의 일회성 `state`·`nonce`, code 교환, ID Token JWS 서명·허용 알고리즘·JWKS와 `iss`·`aud`·`exp`·`nonce` 검증. `aud`가 복수면 `azp`가 현재 `client_id`와 일치해야 한다. 쿼리 콜백 자체가 서명됐다고 가정하지 않는다. 세 제공자 어댑터는 이 불변식을 공유하되 discovery·issuer 별칭·client 인증·claim 변환·오류 매핑 차이만 분리한다.
- **인증 흐름 경계:** 일반 로그인 콜백은 기존 `(issuer, subject)` 연결의 세션만 만들고, 미연결 식별자는 신규 가입으로만 처리한다. 이미 인증된 세션에서는 일반 로그인·신규 가입 시작을 거절하고 로그인 수단 설정 또는 명시적 로그아웃으로 안내한다. 복귀 목적지는 허용 목록에 있는 동일 출처 내부 경로만 보존하며, 신규 사용자는 온보딩, 기존 사용자는 유효한 원래 목적지 또는 기본 대시보드로 보낸다.
- **제공자 토큰:** 인증 완료 후 액세스·리프레시 토큰을 저장하지 않는 것이 기본이다. 불가피한 예외는 해당 스토리에 목적·필드·암호화·만료·폐기 시점을 명시해야 한다. ID Token·code·PKCE verifier·임시 토큰은 검증 또는 흐름 종료 즉시 폐기한다.
- **재인증 허가(`SECURITY-ACTION-1.0`):** 로그인 수단 연결·해제를 포함한 민감 command는 성공한 재인증 후 5분 이내 발급된 서버 보관형 불투명 일회성 action grant를 요구한다. grant는 user·회전된 session·command·target·canonical confirmation hash에 귀속하고 원자적으로 한 번만 소비되며 성공 시 세션 ID를 다시 회전한다. 재인증은 원래 로그인한 제공자가 기본이고 이미 안전하게 연결된 다른 제공자도 선택할 수 있다.
- **삭제 상태 계약:** `identity`가 계정 생명주기·삭제 상태를 소유하고 삭제 진행 여부와 민감 접근·신규 쓰기 허용 여부를 공개 application API로 제공한다. 다른 모듈은 identity 테이블을 직접 읽거나 별도 삭제 상태를 권위 원본으로 만들지 않는다. 사용자·세션·identity 매핑을 만들거나 바꾸는 트랜잭션은 커밋 직전에 계정 상태 잠금으로 삭제 상태를 재검사하고, 삭제 전환도 같은 경계와 경합해 삭제 시작 뒤 신규 세션·identity·일반 쓰기가 커밋되지 않게 한다. identity payload 삭제 후에도 신규 계정·세션 생성을 막는 최소 생명주기 guard는 payload와 분리해 유지한다. 개발·CI는 실제 상태 계약으로 삭제 진행 상태를 설정할 수 있어야 하되, 시험용 상태 변경 기능을 외부 HTTP API로 노출하지 않는다.
- **데이터 규약:** 내부 식별자는 UUID, 외부 식별자는 제공자 namespace와 함께 저장한다. 시각은 저장·외부 원본 모두 UTC `timestamptz`이고 표시와 일자 경계는 `Asia/Seoul`이다. 상태 기반 단일성은 조건부 유일 인덱스로 강제한다. 스키마 변경은 expand 우선의 별도 migration 역할로 실행하고 API·Worker startup은 schema 검증만 한다.
- **테스트:** JUnit·Testcontainers·스텁은 개발·CI에서만 실행한다. 실제 PostgreSQL 통합 시험, 두 사용자 소유권 시험, 삭제·쓰기·세션 생성 경합의 동시성·실패 주입 시험, 모듈 경계 시험을 CI에서 돌린다. 모든 aggregate에 대한 교차 사용자 통합 시험은 이후 에픽에서도 계속 유지한다.

## UX & Interaction Patterns

- 단일 라이트 모드 CSS 토큰 시스템(색상·타이포그래피·간격·모서리·포커스)을 Story 1.1에서 세운다. 다크 모드는 후속 범위다. WCAG 2.2 AA를 기준으로 일반 텍스트 4.5:1, 큰 텍스트와 기능 경계 3:1 이상 대비를 유지한다.
- 한국어 모바일 우선 반응형 `app-shell`: `<768px` 한 열 + 하단 탐색, `768–1023px` 2열, `≥1024px` 최대 4열 + 측면 탐색. 일반 사용자 전역 목적지는 대시보드·조정 이력·설정 셋으로 제한하고 내비게이션에 금융값을 노출하지 않는다.
- `social-sign-in`: 세 제공자를 전체 폭 세로 목록에 동등한 시각 면적과 고정 순서로 배치한다. 로고·명칭·채움색·글자색·테두리·모서리·내부 여백은 각 제공자의 최신 공식 버튼 가이드가 BokriLog 토큰보다 우선하고, BokriLog는 순서·간격·최소 목표 크기·포커스 링만 소유한다. 추천 표지, 마지막 사용 제공자 강조, 로고만 있는 버튼, 임의 브랜드 색 변경은 금지한다. 접근 가능한 이름은 제공자명 + "계속하기"다. 기본으로 새 창을 열지 않고, 제공자 왕복 뒤 포커스를 페이지 제목 또는 오류 요약으로 보낸다. 버튼 아래에 소셜 계정은 본인 확인에만 사용하며 Bybit·금융·계획 데이터를 공유하지 않는다는 안내를 둔다.
- 모든 핵심 화면에 `복리 계획 비교`와 "투자성과·계좌 수익률·투자 추천이 아닙니다" 고지를 인접 배치한다. 실시간·정확 보장, 수익 축하, 손실 공포, 스트릭·보상 표현은 금지한다.
- 키보드·접근성 바닥선: 모든 핵심 조작은 `Tab` 도달과 `Enter`/`Space` 실행이 가능하고, 전역 `focus-visible`, 라우트 전환 후 제목 포커스, 대화상자 포커스 트랩과 호출점 복귀, 고정 탐색·오버레이·화면 키보드에 포커스가 가려지지 않는 안전 영역, 최소 44×44px 목표 크기를 적용한다. 화면당 polite `role="status"` live region은 하나만 두고 갱신 영역에 `aria-busy`, 단계 목록에 `aria-current`, 실패 시 오류 요약 포커스를 적용한다.
- 320 CSS px과 400% 확대에서 양방향 스크롤 없이 핵심 과업을 수행하고 200% 확대에서 텍스트가 잘리지 않는다. `prefers-reduced-motion`에서는 전환·스피너를 정적 표지로 대체한다.
- 네트워크 단절 시 변경 조작을 실행 전에 차단하고 입력을 보존하며 자동 재시도하지 않는다. 로그아웃·세션 만료·삭제 후 뒤로 가기 복원으로 민감 화면이 노출되지 않아야 한다.
- 취소·제공자 장애·콜백 실패에서 복귀 경로와 목적지 복원을 제공한다. 제공자 접근을 잃었을 때 연결된 다른 수단이 있으면 그 방법을 제시하고, 하나뿐이면 해당 제공자의 공식 계정 복구로 안내하며 이메일만으로 인증을 우회하지 않는다. 복구 중 금융 화면과 계정 존재 여부를 노출하지 않는다.
- 연결·개인정보 설정 화면이 로그인 수단 연결·해제를 관리한다. 해제는 `confirmation-dialog`로 대상·비가역 결과·삭제되는 데이터와 보존되는 데이터를 구분해 설명하고 기본 포커스를 취소에 둔다.

## Cross-Story Dependencies

- **선행 에픽 없음.** Epic 2~5는 모두 Epic 1에 의존하며, `identity`의 공개 소유권·삭제 상태 API를 통해서만 접근한다.
- **기반 사슬:** Story 1.1(프런트엔드 셸·토큰) → 1.2(Spring Boot·상태 API·Nginx 동일 출처) → 1.3(`identity` 모듈·PostgreSQL 마이그레이션·소유권/삭제 상태 계약)은 순차 의존이다. 1.3의 소유권·삭제 상태 계약은 이후 모든 인증 스토리와 이후 에픽이 재사용한다.
- **제공자 확장:** Story 1.4(Google)가 공통 OIDC·세션 계약을 확립하고 1.6(네이버)·1.7(카카오)이 이를 재사용한다. 1.6과 1.7은 서로 독립이다. 1.5(로그아웃·만료·의심 세션)는 1.4의 세션 위에서 동작한다.
- **민감 작업 사슬:** Story 1.8(재인증·세션 회전) → 1.9(5분·일회성 action grant) → 1.10(연결)·1.11(해제)이 1.8~1.9의 재인증·허가를 소비한다. 1.10·1.11이 세 제공자를 모두 다루려면 1.7이 선행되어야 한다.
- **다른 에픽으로 넘기는 범위:** 사용자에게 노출되는 계정 삭제 화면과 전체 삭제 orchestration은 Epic 5가 소유한다. 삭제 완료 후 동일 제공자의 빈 신규 계정 생성 허용 여부와 guard의 법정 보존 범위·파기 시점도 Epic 5의 확정 정책이다. 해제·삭제된 identity가 백업 복원에서 되살아나지 않는 시험은 백업·복원 기능을 도입하는 후속 에픽에서 수행하며 Story 1.11 완료를 여기에 의존시키지 않는다. Bybit 자격 증명 등록·교체·해제와 계획 중도 종료는 1.9의 허가 계약을 소비하는 Epic 2의 범위다.
- **외부 게이트:** 세 제공자의 실제 클라이언트 등록과 production secret은 스토리 완료를 막지 않는 별도 게이트다. 개발·CI는 스텁으로 진행하고 실연동 검증은 등록 완료 후 별도로 선언한다.
