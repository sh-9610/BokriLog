# PRD Quality Review — BokriLog MVP

## Overall verdict

**전체 판정: adequate.** 기준선 보존이라는 제품 명제, 명시적인 MVP/Later 경계, 실패 시 마지막 정상값을 지키는 원칙, 계산·보안·광고의 검증 가능한 요구사항은 공개 베타 결정을 지지할 만큼 잘 서 있다. 다만 §12.2에 “MVP 범위를 바꾸지 않는 구현 결정”으로 묶인 항목 중 일부가 실제로는 UX·아키텍처·데이터 정확성의 선행 결정이며, 후속 계획의 시작 기준과 주기 경계 계산이 아직 단일한 구현으로 수렴하지 않아 이 상태 그대로 에픽·스토리로 넘기면 팀마다 다른 결과를 만들 위험이 있다.

## Decision-readiness — adequate

§1은 “더 많은 투자 분석이 아니라 기준선 보존”이라는 선택을 분명히 하고, §8–§9는 TWR/MWR, 다중 거래소, 백그라운드 수집 등을 명시적으로 포기한다. 광고도 매 수동 동기화 때 노출을 요청하되 실제 노출을 보장하지 않고, 실패가 조회를 막지 않는다는 절충이 §5.6과 SM-C1/SM-C3에 연결되어 있어 의사결정의 흔적이 보인다.

반면 §12.2의 일곱 항목은 단순 구현 세부사항으로 보기 어렵다. 특히 인증 방식, 지원 UTA/사건 허용목록, 환산가 출처, 강한 신호 판정표는 UX·데이터 모델·운영 통제를 좌우하며, §11의 출시 전 게이트를 통과하기 위한 선행 결정이다. 누가 언제 무엇을 결정하는지가 없으므로 바로 설계·개발을 승인하기에는 한 단계 부족하다.

### Findings

- **high** 단계 차단 결정을 구현 세부사항으로 축소함 (§12.2, §11) — 인증 방식, 지원 UTA/외부 자금흐름 허용목록, 환산가 출처, 강한 신호 정의는 각각 UX·아키텍처·공식 계산·자동 정지를 바꾸는 선행 결정인데 “MVP 범위를 바꾸지 않는 항목”으로만 분류되어 있다. *Fix:* 각 항목에 결정 책임자, 결정 기한, 차단되는 후속 단계(UX/아키텍처/계산 SPEC/출시)를 붙이고, 최소한 2·3·6번은 phase-blocker로 승격한다.
- **medium** Day 90 고정 IP 정책의 결정 근거와 사용자 전환 경로가 없음 (§10, §11) — “IP 제한 없는 키 신규 연결 중단”은 보안상 강한 제품 정책이지만, 어떤 위험을 줄이는지와 기존 사용자·동적 IP 사용자에게 무엇을 제공할지가 명시되지 않았다. *Fix:* 정책 목적, 적용 대상(기존 연결 포함 여부), Day 60 판단과의 관계, 지원하지 못하는 사용자에게 보일 상태/안내를 요구사항으로 확정하거나 별도 오픈 결정으로 표시한다.

## Substance over theater — strong

문서의 대부분은 제품 고유의 제약에서 나온 내용이다. `totalEquity`, UTA 경계, 외부 자금흐름, 사건 시점 환산, 마지막 정상 스냅샷, 세 가지 독립 신뢰 상태가 서로 연결되어 있어 일반적인 금융 대시보드 문구로 대체할 수 없다. NFR도 계산 회귀 100%, LCP/INP/CLS, 자동·수동 정지 시간, 운영 비용처럼 측정 가능한 경계를 제시하며, 단일 대표 사용자 민준은 실제 광고·실패·계산 보류 동작을 견인한다.

격리·비상정지 요구는 개인 프로젝트 규모에 비해 무거워 보일 수 있으나, 외부 API 자격정보와 재무 수치를 다루는 공개 베타이며 NFR/성공 기준/출시 게이트까지 연결되어 있어 단순 장식으로 판단하지 않는다.

## Strategic coherence — strong

§1의 제품 명제는 “최초 계획과 자금흐름 조정 이력을 보존한 계획선 비교”이고, FR-4~FR-13은 계획 불변성, 외부 자금흐름 격리, 동일 스냅샷, 신뢰 상태라는 하나의 흐름을 따른다. 수익화 기능인 FR-14~FR-15도 핵심 조회를 훼손하지 않는 보조 축으로 제한되어 있다.

SM-3의 반복 가치, SM-5의 개념 이해, SM-7~SM-9의 안전 결과와 선행통제가 명제를 검증하며, SM-C1~SM-C3이 광고와 상태 표현의 역효과를 견제한다. 광고 수익 최소치를 Day 60 계속/중단 기준으로 두지 않은 점도 초기 12명 베타에서 수익성보다 가치·신뢰를 먼저 검증한다는 범위 논리와 일치한다.

## Done-ness clarity — adequate

FR-1~FR-17에는 모두 검증 가능한 결과가 있고, §6은 주요 오류·결측·음수·광고 실패를 구체적 제품 동작으로 바꾼다. §4는 표시 반올림, 계산 불가, 음수·100% 초과 허용까지 정의해 일반적인 PRD보다 완료 조건이 선명하다.

그러나 “기존 계획 종료 후 새 계획 생성”의 새 기준점, 전면광고 응답 지연의 상한, 자동 정지를 유발하는 강한 신호가 결정되지 않았다. 이 세 가지는 정상/실패 테스트를 작성할 때 즉시 갈라지는 부분이다.

### Findings

- **high** 두 번째 이후 계획의 시작금액·시작시각 확정 규칙이 없음 (§5.2 FR-4, FR-5) — FR-4는 “첫 정상 연결”과 “첫 정상 스냅샷”만 정의하지만 FR-5는 기존 계획을 종료하고 새 계획을 만들 수 있다고 한다. 새 계획이 최초 연결 금액을 재사용하는지, 생성 시 최신 정상 스냅샷을 사용하는지, 동기화를 강제하는지 알 수 없다. *Fix:* 후속 계획 생성 시 최신 정상 동기화를 요구하고 그 스냅샷의 `totalEquity`와 측정 시각을 새 `P0`, `t0`로 고정하는지 명시하며, 신뢰 상태가 불량하거나 연결이 해제된 경우의 생성 차단 조건도 추가한다.
- **medium** 광고 로드 대기의 종료 조건이 없음 (§5.6 FR-14, FR-15; §7.3 NFR-16) — 광고 미채움·오류 시 결과를 보여준다고 했지만 광고 SDK가 응답하지 않는 경우 사용자가 얼마나 기다린 뒤 결과로 진행하는지 정의되지 않았다. *Fix:* 광고 요청의 최대 대기시간과 타임아웃 시 즉시 결과 표시라는 검증 가능한 조건을 둔다.
- **medium** 자동 정지의 입력 조건이 자리표시자로 남음 (§5.7 FR-17; §12.2 6번) — “정의된 강한 신호” 후 60초라는 시간만 있고 어떤 사건이 강한 신호인지 아직 없어 FR-17 자동 정지 테스트를 만들 수 없다. *Fix:* 최소 신호군(예: 쓰기 권한 키 수용, 교차 사용자 접근, 계산 회귀 불일치, 비밀 노출 탐지)과 각 신호가 중단하는 범위를 PRD 또는 필수 선행 판정표에 연결한다.

## Scope honesty — adequate

§8.2는 투자성과, 주문, 다중 거래소, 백그라운드 수집, 강제 광고 시청을 직접 비목표로 선언하고 §9는 Later가 현재 아키텍처에 숨은 준비 요구를 만들지 않는다고 못 박는다. 이는 MVP 범위 확장을 효과적으로 차단한다. 사용자에게 확인된 사항을 반영해 §12.1을 “없음”으로 둔 것도 형식적인 가정 목록을 만들지 않아 좋다.

다만 §12.2의 항목들은 단순히 나중에 고를 수 있는 선택과 공식 계산·운영 안전을 정의하는 차단 결정을 섞고 있다. 오픈 아이템의 개수보다 분류가 문제이며, 이 상태에서는 downstream 팀이 자기 가정을 문서 밖에서 채울 가능성이 있다.

### Findings

- **medium** 오픈 항목의 결정 영향과 기본 실패 동작이 분리되지 않음 (§12.2) — 광고 공급자처럼 교체 가능한 선택과 외부 자금흐름 허용목록·환산가 출처처럼 공식 계산 가능 범위를 정하는 선택이 같은 등급으로 놓여 있다. *Fix:* `설계 착수 전`, `개발 착수 전`, `출시 전`으로 나누고, 미결정 시 기본값(예: 지원 사건 없음/추정 계산 비활성/광고 비활성)을 명시해 숨은 범위 확장을 막는다.
- **low** 연결 해제 뒤 재연결·새 계획 전환 범위가 명시되지 않음 (§5.1 FR-3, §6) — 기존 계획은 읽기 전용 보존된다고 확정했지만 동일 사용자가 재연결할 수 있는지, 재연결 후 기존 계획을 재활성화할 수 있는지는 독자가 추론해야 한다. *Fix:* 재연결 허용 여부와 재연결은 항상 새 계획으로 시작하는지 여부를 MVP 포함/비목표에 한 줄로 확정한다.

## Downstream usability — adequate

용어집이 제품의 핵심 도메인 명사를 수식과 FR에서 동일하게 사용할 수 있게 하고, FR 1–17·UJ 1–3·SM 1–10의 ID는 연속적이고 고유하다. UJ마다 민준이라는 이름 있는 주인공이 있으며, 대표 여정은 정상 동기화·광고·실패 저하를 한 흐름으로 묶는다. `addendum.md`는 구현 인계사항을 본문에서 잘 분리한다.

가장 큰 위험은 `periods(a,b)`가 모든 경계 조합에서 유일한 값을 내도록 정의되지 않았다는 점과, 계획/연결/신뢰 상태의 전이 규칙이 문장 여러 곳에 분산되어 있다는 점이다. 계산 SPEC과 상태 설계가 이를 보완할 예정이지만, 현재 PRD만 source-extract하면 서로 다른 해석이 가능하다.

### Findings

- **high** 복리 주기 경계 정의가 경계 사례에서 결정적이지 않음 (§4.1–§4.3) — “계획 시작 시각에 고정된 주기 경계”와 “부분 주기는 해당 달력 주기의 실제 길이 대비 경과시간”만으로는 월말(1월 29~31일 시작), DST와 무관한 서울 시간대라도 윤일, 중간 시점 입출금이 주기 경계를 가로지를 때의 분할 방식이 유일하게 정해지지 않는다. 이는 `Plan(t)`와 `Target(t)`의 공식값을 바꾼다. *Fix:* 일·주·월별 경계 생성 규칙, 존재하지 않는 월 일자의 보정 규칙, 부분 주기 합산 알고리즘을 정의하고 대표 고정 예제를 계산 SPEC 출시 게이트에 명시한다.
- **medium** 종료 이후 공식의 평가 구간이 불명확함 (§4.2–§4.7, FR-13) — 완료 후 현재가치는 계속 갱신한다고 했지만 `Plan(t)`가 `t > T`에서도 계속 복리되는지, `T`로 고정되는지 본문 수식의 정의역이 없다. *Fix:* 활성 계획 지표는 `t ≤ T`에서만 평가하고 종료 후에는 완료 스냅샷 기준 값을 고정하는지, 혹은 `min(t,T)`를 사용하는지 명시한다.
- **medium** 제품 상태 전이가 여러 절에 흩어져 있음 (§4.7, FR-3, FR-5, FR-9, FR-13, FR-16) — `활성`, `검토 필요`, `중도 종료`, `완료`, `연결 해제 후 읽기 전용`, `격리` 사이의 허용 전이와 동기화/새 계획 생성 가능 여부를 한 절에서 추출하기 어렵다. *Fix:* 구현 메커니즘이 아닌 제품 상태·전이 표를 추가하고 각 상태에서 조회, 동기화, 종료, 새 계획 생성 가능 여부를 명시한다.
- **low** UJ-2와 UJ-3가 UJ-1보다 압축되어 독립 추출성이 낮음 (§2.3) — 두 여정 모두 이름 있는 주인공은 있으나 진입 상태·종료 상태·예외가 한 문단에 합쳐져 UX가 관련 요구사항을 역추적하기 어렵다. *Fix:* UJ-2와 UJ-3도 UJ-1과 같은 최소 구조로 펼치고 관련 FR ID를 붙인다.

## Shape fit — strong

개인 프로젝트이면서 실제 공개 베타 운영이 목표인 제품에 맞춰, 단일 대표 사용자와 세 개의 핵심 여정만 두고 나머지는 기능·계산 중심으로 구성했다. 소비자용 모바일·데스크톱 웹에서 광고와 신뢰 상태가 사용자 경험에 직접 영향을 주므로 UJ가 필요하며, 동시에 정확한 계산과 외부 API 경계가 핵심이라 capability 중심 FR과 NFR을 충분히 둔 혼합 형태가 적합하다.

두 페이지 수준의 취미 PRD보다 길지만, 금융 자격정보·공식 수치·광고·1인 운영이라는 출시 리스크가 있어 상세도가 정당화된다. 구현 세부사항은 addendum과 후속 계산 SPEC으로 넘겨 본문이 기술 설계 문서로 변하는 것도 막았다.

### Findings

별도 finding 없음.

## Mechanical notes

- **ID 연속성:** FR-1~FR-17, UJ-1~UJ-3, SM-1~SM-10은 중복·누락 없이 연속적이다. 역지표는 별도 접두어 SM-C1~SM-C3으로 일관된다.
- **교차 참조:** UJ·FR·SM 간 참조는 존재하는 ID로 해소된다. §4, §6, §11, §12 참조도 유효하다.
- **용어:** `현재가치`, `현재 시점 계획금액`, `조정 최종 목표`, `신선도`, `입력 신뢰도`, `계산 성격`은 용어집과 본문에서 대체로 일관된다. 다만 `정상 조회`, `유효 동기화 시도`, `강한 신호`는 성공 기준/NFR에서 새로 정의되거나 미정 상태이므로 후속 용어집 보강 후보이다.
