# PRD–UX 최신 결정 조정 보고서

- 작성일: 2026-08-23
- 대상 PRD: `prd.md`, `addendum.md`, PRD `.memlog.md`
- 최신 결정 근거: UX `EXPERIENCE.md`, UX `.memlog.md`
- 목적: 확정된 UX·운영 결정을 PRD에 반영할 때의 충돌, 누락, 정확한 수정 위치를 식별한다.
- 제한: 이 보고서는 조정안만 기록하며 `prd.md`, `addendum.md`, 각 `.memlog.md`는 변경하지 않는다.

## 1. 조정 판정

현재 PRD의 핵심 제품 경계와 계산 계약은 유지할 수 있다. 다만 다음 네 묶음은 최신 UX 결정과 충돌하거나 검증 가능한 제품 요구사항으로 충분히 고정되지 않았다.

1. Google·네이버·카카오 소셜 로그인과 다중 로그인 수단 연결은 UX에서 확정됐지만 PRD §12에는 아직 미결정으로 남아 있다.
2. 무료·유광고 및 비개인화 문맥형 광고 방향은 일치하지만, `매 수동 동기화 성공 시 요청` 문구가 `30분당 최대 1회·하루 최대 3회` 결정과 충돌한다. 광고 공급자 미확정 시 무광고 출시라는 PRD 기본 동작도 폐기돼야 한다.
3. 계정 삭제의 사용자·금융 데이터 삭제, 최소 법정 기록 분리 보존, 백업 최대 30일 파기가 NFR-10에 충분히 구체화되지 않았다.
4. 지원 채널, 영업일 3일 이내 답변, 서비스 내부 장애·복구 공지가 §12의 미결정 상태로 남아 있다.

라이트 모드 전용 MVP는 범위 문구에 반영할 수 있다. 네 개 핵심 목업은 UX 납품·검증 범위이므로 PRD 기능 요구사항으로 편입하지 않는다.

## 3. 요구사항별 권장 변경

### 3.1 인증과 계정 경계

#### §2.3 핵심 사용자 여정

UJ-2의 시작 전에 다음 제품 행동을 추가한다.

> 민준은 Google·네이버·카카오 중 하나로 가입한다. BokriLog는 소셜 제공자를 본인 확인에만 사용하며 금융·계획·Bybit 데이터를 제공자와 공유하지 않는다. 로그인 성공 뒤 기존 외부 식별자가 없으면 새 BokriLog 사용자 계정을 만들고 온보딩으로 이동한다.

로그인 수단 연결·복구를 UJ-2의 예외 또는 별도 짧은 여정으로 추가한다.

> 민준은 로그인된 설정에서 현재 로그인 수단으로 재인증한 뒤 다른 제공자를 같은 BokriLog 계정에 연결할 수 있다. 제공자 장애 시 이미 연결된 다른 수단을 직접 선택한다. 하나의 수단만 연결된 경우 BokriLog가 이메일 확인으로 우회하지 않고 해당 제공자의 공식 복구 절차로 안내한다.

#### §3 용어집

`사용자 계정`을 다음처럼 보강하고 `로그인 수단`을 추가한다.

> **사용자 계정** — BokriLog의 불투명한 내부 `user_id`가 소유하는 인증·데이터 경계. MVP에서 제공자별 로그인 수단 1~3개, Bybit 연결 1개, 활성 계획 최대 1개를 가진다.

> **로그인 수단** — Google·네이버·카카오가 발급한 고유 외부 식별자 `(issuer, subject)`와 한 BokriLog `user_id`의 연결. 이메일·표시명은 식별키나 자동 병합 근거가 아니다.

#### FR-1: 사용자 데이터 경계

현재 소유권·교차 사용자 접근·Bybit 연결 1개 조건은 유지한다. 다음 검증 결과를 추가한다.

- 모든 사용자 데이터는 외부 제공자 식별자가 아니라 BokriLog 내부 `user_id`에 귀속한다.
- 동일한 `(issuer, subject)`는 둘 이상의 `user_id`에 연결할 수 없다.
- 이메일 주소가 같다는 이유로 계정을 자동 병합·전환하거나 기존 계정 존재 여부를 노출하지 않는다.

#### 신규 FR-18 권장: 소셜 인증과 로그인 수단 관리

기존 FR ID는 재번호화하지 않고 다음 전역 ID를 추가한다.

> 사용자는 Google·네이버·카카오 중 하나로 가입·로그인할 수 있고, 로그인된 설정에서 재인증을 거쳐 다른 제공자를 같은 BokriLog 사용자 계정에 연결하거나 마지막 수단이 아닌 연결을 해제할 수 있다.

검증 가능한 결과:

- MVP는 Google·네이버·카카오 3개 제공자를 지원하고 BokriLog 비밀번호·이메일 링크·SMS 로그인은 제공하지 않는다.
- 신규 외부 식별자는 일반 로그인 콜백에서 새 계정으로 처리하며, 로그인된 계정에서 시작한 명시적 연결 절차에서만 기존 `user_id`에 추가한다.
- 로그인 수단 추가는 현재 연결 수단 재인증과 새 제공자 인증을 모두 성공한 뒤 원자적으로 완료한다.
- 마지막 로그인 수단은 해제할 수 없다.
- 민감 작업인 Bybit 연결 생성·교체·해제, 로그인 수단 연결·해제, 계정 삭제와 의심 세션 이후에는 최근 인증을 요구한다.
- 제공자 취소·거부·장애·콜백 검증 실패 시 계정이나 연결 상태를 바꾸지 않으며 다른 제공자를 자동 선택하지 않는다.
- 소셜 제공자에는 인증에 필요한 최소 정보만 요청하고 Bybit 자격정보, 금융값, 계획, 조정 이력을 전달하지 않는다.

#### NFR-8·NFR-9

- NFR-8에 제공자 액세스·ID·리프레시 토큰을 화면, URL, 브라우저 저장소, 로그, 분석, 광고 도구에 기록하지 않는 조건을 추가한다.
- NFR-9에 `user_id` 소유권과 `(issuer, subject)` 유일성, 이메일 기반 자동 병합 금지를 추가한다.
- Authorization Code, PKCE, `state`, `nonce`, 콜백 서명·클레임 검증 같은 기술 수단은 제품 요구의 검증 방법으로 addendum 또는 아키텍처에 둔다. PRD 본문에는 결과 계약만 남긴다.

### 3.2 광고 모델과 출시 게이트

#### UJ-1

`동기화가 정상 완료되면 전면광고가 노출된다`는 확정적 문구를 다음처럼 바꾼다.

> 동기화가 정상 완료되고 사용자 동의·채움·접근성·빈도 조건을 충족하면 닫기 가능한 전면광고 노출을 시도한다. 최근 30분 안에 광고를 시도했거나 당일 시도 횟수가 3회에 도달했다면 광고를 요청하지 않고 저장된 최신 결과로 이동한다.

#### FR-14: 수동 동기화 광고 노출 시도

다음 두 항목을 교체·추가한다.

- 기존 `매 수동 동기화 성공 시 광고 노출을 요청` 문구를 삭제한다.
- `수동 동기화 성공 후 광고 노출 시도는 사용자당 30분에 최대 1회, Asia/Seoul 기준 하루 최대 3회로 제한한다. 제한에 걸린 동기화는 광고 요청 없이 같은 저장 결과로 이동한다.`를 추가한다.

`시도`의 측정 지점은 공급자 요청 생성 시점으로 정의하는 것이 SM-10과 중복·재진입 억제에 가장 명확하다. 정확한 원자적 카운터·중복 요청 처리 방식은 addendum 또는 아키텍처가 소유한다.

#### FR-15: 광고 실패와 개인정보 경계

기존 fail-open과 데이터 최소화 조건은 유지하고 다음을 추가한다.

- 실제 광고가 키보드·스크린리더 접근성 승인 조건을 만족하지 못하거나 iframe 포커스 이탈이 불가능하면 광고를 건너뛰고 저장된 최신 결과를 표시한다.
- 광고 동의 철회는 다음 광고 요청부터 적용하며 핵심 기능을 제한하지 않는다.
- 광고가 실패하거나 건너뛰어져도 빈도 제한을 우회하기 위한 자동 재요청을 하지 않는다.

#### NFR-15·NFR-16

- NFR-15의 키보드 접근 범위를 광고 닫기와 광고 후 결과 이동까지 확장한다.
- NFR-16을 `iframe 밖의 즉시 사용 가능한 닫기, 논리적·가시적 포커스, 키보드 트랩 없음, 스크린리더 이름, 자동재생 음성·과도한 깜빡임 없음, 확대·리플로, 오류·시간초과 시 fail-open`의 실제 소재 승인 기준으로 보강한다.
- 실제 공급자·소재·SDK 버전으로 키보드와 스크린리더 시험을 통과하지 못하면 유광고 공개 베타를 출시하지 않는다고 명시한다.

#### §11 출시 전 게이트

광고 게이트를 다음처럼 교체한다.

> 구현 단계에서 광고 공급자와 전면광고 형식을 선정하고 비개인화 문맥형 모드, 동의 문구, 실제 제3자 데이터 흐름, 공식 트리거, 30분·일일 빈도 제한, 닫기·미채움·차단·오류 fail-open을 검증한다. 실제 광고 소재로 키보드·스크린리더 접근성 승인 시험을 통과해야 하며, 공급자나 접근성에 영향을 주는 SDK·소재가 바뀌면 재시험한다.

#### §12 미결정 사항 등록부

현재 광고 행에서 `빈도 제한`은 제거한다. `미확정 시 기본 동작: 광고 없이 베타 출시`는 최신 유광고 결정과 충돌하므로 다음처럼 바꾼다.

| 결정 | 책임자 | 기한·차단 단계 | 미확정 시 기본 동작 |
|---|---|---|---|
| 광고 공급자·공식 트리거·실제 데이터 흐름·동의 문구와 접근성 승인 | 제품·개인정보 책임자 | 구현 단계 광고 통합 및 공개 베타 배포 전 | 유광고 베타 출시 차단 |

#### addendum B

- `수동 동기화가 성공할 때마다 광고 노출을 요청`을 `성공 후 빈도 조건을 충족할 때만 요청`으로 바꾼다.
- 사용자당 30분 최대 1회, `Asia/Seoul` 하루 최대 3회, 공급자 요청 생성 시점 기준 카운트와 중복·재진입 시 재요청 금지를 구현 인계사항으로 추가한다.
- 공급자 선정은 구현 단계에서 수행하지만 출시 전 데이터 흐름·접근성 승인을 통과해야 한다고 명시한다.

### 3.3 계정 삭제와 법정 보존

#### 신규 FR-19 권장: 사용자 계정 삭제

> 사용자는 최근 인증과 명시적 확인을 거쳐 BokriLog 계정 삭제를 요청할 수 있다. 완료되면 모든 세션을 종료하고 사용자·금융 데이터를 다시 조회할 수 없게 한다.

검증 가능한 결과:

- 소셜 로그인 연결·제공자 토큰, Bybit 자격정보, 계획, 외부 자금흐름, 스냅샷, 계산 결과·버전과 광고 동의를 운영 데이터에서 삭제한다.
- 법률상 필요한 최소 보안·관리자 접속기록만 대상·근거·목적·기간을 확정해 사용자 데이터와 분리 보관하고 Bybit 자격정보나 금융 상세값을 포함하지 않는다.
- 삭제된 계정의 백업은 서비스 복구에 사용하지 못하게 격리하고 계정 삭제 요청일부터 최대 30일 안에 파기한다.
- 화면과 개인정보 처리방침은 운영 데이터 삭제 시점, 백업 파기 예정일, 법정 분리 보존 대상·목적·기간을 구분해 알린다.
- 일부 삭제 실패를 완료로 표시하지 않고 중복 요청과 삭제 중 민감 화면 접근을 차단한다.

#### NFR-10

현재 문구를 다음 계약으로 구체화한다.

> 계정 삭제 시 소셜 인증 연결·제공자 토큰·Bybit 자격정보와 모든 사용자·금융·계획·계산 데이터를 운영 환경에서 삭제하고 세션을 폐기해야 한다. 법률상 필요한 최소 기록은 대상·법적 근거·목적·기간을 고지해 분리 보관하며, 삭제 계정의 백업은 최대 30일 이내 파기해야 한다.

#### NFR-18

백업 복원 시험에 다음 조건을 추가한다.

- 이미 삭제된 계정은 복원 후에도 서비스 활성 데이터로 되살아나지 않는다.
- 삭제 격리 목록과 최대 30일 파기 일정이 복원·백업 교체 과정에서도 유지된다.

#### §11·§12

- §11에 무료 베타의 정확한 법정 보존 대상·근거·목적·기간과 개인정보·금융 관련 법적 지위를 출시 전 검토하고 개인정보 처리방침·삭제 화면에 반영하는 게이트를 추가한다.
- §12에는 백업 기한이 아니라 아직 남은 법률 판정만 등록한다.

| 결정 | 책임자 | 기한·차단 단계 | 미확정 시 기본 동작 |
|---|---|---|---|
| 계정 삭제 후 최소 법정 보존 기록의 대상·법적 근거·목적·기간 | 제품·개인정보 책임자 | 개인정보 처리방침 확정 및 공개 베타 배포 전 | 베타 출시 차단 |

### 3.4 사용자 지원과 장애 공지

#### FR-17 보강 또는 신규 FR-20 권장

> 사용자는 웹 문의 폼 또는 공개 지원 이메일 중 최소 하나로 문의할 수 있고, 서비스는 접수 사실과 영업일 기준 3일 이내 답변 목표를 안내한다. 전체 또는 범위별 장애·복구 상태는 인증 후 서비스 내부 공지로 확인할 수 있다.

검증 가능한 결과:

- `영업일`의 달력·휴일 기준과 자동 접수 응답 문구는 운영 정책에서 확정한다.

지원 운영 시간 산정에 문의 접수·답변과 장애 공지 갱신을 명시적으로 포함한다. 영업일 기준 3일 이내 답변 목표의 달성률을 운영 지표로 측정한다. 수동 보안 사고 대응 시간대는 지원 답변 목표와 별개다.

기존 `사용자 지원 채널·사고 공지·운영 대응 시간대` 행은 세 항목을 하나로 묶어 확정 상태를 숨긴다. 지원 채널·답변 목표·공지 위치는 등록부에서 제거하고, 아직 남은 항목만 다음처럼 유지한다.

|---|---|---|---|
| 중대 사고의 수동 운영 대응 시간대와 당직 범위 | 보안·운영 책임자 | 공개 베타 배포 전 | 수동 24시간 대응을 약속하지 않고 자동 정지를 일차 통제로 유지하되, 공개 베타 출시 여부는 보안 검토에서 판정 |

## 9. 반영 완료 판정 기준

다음이 모두 참이면 PRD–UX 조정이 완료된 것으로 본다.

- §12에서 인증 방식이 더 이상 미결정이 아니다.
- FR-1 및 인증 전용 FR이 내부 `user_id`, `(issuer, subject)` 유일성, 명시 연결, 자동 병합 금지를 검증 가능하게 정의한다.
- FR-14와 addendum B 어디에도 `매 성공 시 공급자 요청`이 남아 있지 않고 30분·일일 제한이 일치한다.
- 광고 미확정의 기본 동작이 `광고 없이 출시`가 아니라 `유광고 베타 출시 차단`이다.
- 실제 광고 소재의 접근성 승인과 데이터 흐름 검증이 §11 출시 게이트다.
- 계정 삭제 범위와 백업 최대 30일 파기가 FR·NFR에 모두 연결되고 삭제 계정 복원 방지가 시험된다.
- 지원 채널·답변 목표·장애 공지가 확정 요구사항이며, §12에는 수동 사고 대응 시간대만 남는다.
- 라이트 모드는 MVP 포함, 다크 모드는 MVP 제외로 표시된다.
- 네 개 목업은 UX 산출물로만 관리되고 PRD에는 그 제품 행동만 남는다.
